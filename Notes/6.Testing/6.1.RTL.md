# React Testing Library (RTL)

### What is React Testing Library?

React Testing Library (RTL) is the most popular library for testing React applications.

It focuses on **testing the application the way a user uses it**, instead of testing internal implementation details.

> **Interview Line:**
> "RTL encourages testing behavior rather than component internals."

---

## Why use RTL?

Instead of checking:

* state
* methods
* component instance

RTL checks:

* Is the text visible?
* Can the user click the button?
* Does the form submit?
* Is an error message displayed?

This makes tests less fragile.

---

## Basic Flow

```jsx
render(Component)
↓

Find Element

↓

Perform Action

↓

Verify Result
```

---

## render()

Renders the component into a virtual DOM.

```jsx
import { render } from '@testing-library/react';

render(<Login />);
```

---

## Queries

RTL provides queries to find elements.

### getBy...

Used when element **must exist**.

```jsx
screen.getByText("Login");
```

If not found → test fails.

---

### queryBy...

Used when element **may not exist**.

```jsx
expect(screen.queryByText("Error")).toBeNull();
```

Returns `null` instead of throwing an error.

---

### findBy...

Used for **async UI**.

Example:

```jsx
const message = await screen.findByText("Success");
```

Useful after API calls.

---

## Common Queries

### By Text

```jsx
screen.getByText("Submit");
```

---

### By Role (Recommended)

Most preferred.

```jsx
screen.getByRole("button");
```

or

```jsx
screen.getByRole("button", {
  name: /submit/i
});
```

---

### By Label

Useful for forms.

```jsx
screen.getByLabelText("Username");
```

---

### By Placeholder

```jsx
screen.getByPlaceholderText("Search");
```

---

### By TestId

```jsx
<button data-testid="save-btn">
```

```jsx
screen.getByTestId("save-btn");
```

Use only when semantic queries are not possible.

---

## userEvent

Simulates real user interactions.

```jsx
import userEvent from "@testing-library/user-event";
```

Click

```jsx
await userEvent.click(button);
```

Type

```jsx
await userEvent.type(input, "React");
```

Clear

```jsx
await userEvent.clear(input);
```

---

## Assertions

Using Jest matchers.

```jsx
expect(button).toBeInTheDocument();
```

```jsx
expect(input).toHaveValue("React");
```

```jsx
expect(button).toBeDisabled();
```

```jsx
expect(message).toHaveTextContent("Success");
```

## Example

Component

```jsx
function Counter() {
  const [count, setCount] = useState(0);

  return (
    <>
      <p>{count}</p>
      <button onClick={() => setCount(count + 1)}>
        Increment
      </button>
    </>
  );
}
```

Test

```jsx
import { render, screen } from "@testing-library/react";
import userEvent from "@testing-library/user-event";

test("increments counter", async () => {
  render(<Counter />);

  await userEvent.click(
    screen.getByRole("button", {
      name: /increment/i
    })
  );

  expect(screen.getByText("1")).toBeInTheDocument();
});
```

---

## Best Practices

✅ Test what the user sees.

✅ Prefer `getByRole()` over `getByTestId()`.

✅ Use `userEvent` instead of `fireEvent` (more realistic).

✅ Avoid testing implementation details like state or internal methods.

# Common Interview Questions

### 1. Why React Testing Library instead of Enzyme?

**Answer:**
RTL tests components the way users interact with them, while Enzyme focuses more on implementation details. RTL is now the recommended approach.

---

### 2. Difference between `getBy`, `queryBy`, and `findBy`?

* **getBy** → Element should exist immediately.
* **queryBy** → Returns `null` if element doesn't exist.
* **findBy** → Waits for async elements (returns a Promise).

---

### 3. Why is `getByRole` recommended?

Because it matches how assistive technologies identify elements, improves accessibility, and makes tests more resilient.

---

### 4. Why use `userEvent` instead of `fireEvent`?

`userEvent` simulates real user interactions (clicks, typing, tabbing) more accurately, while `fireEvent` triggers low-level DOM events directly.

---

### 5. What should you avoid testing with RTL?

Avoid testing implementation details such as component state, internal methods, or lifecycle logic. Focus on what the user can see and do.
