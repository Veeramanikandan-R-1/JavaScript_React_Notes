# React Testing Library (RTL) — Interview Notes

For a **5-year experienced React developer**, focus on the **testing philosophy, queries, user interactions, async behavior, mocking, and real-world component testing** rather than memorizing APIs.

---

## 1. What is React Testing Library?

**React Testing Library (RTL)** is a testing utility for testing React components from the **user's perspective**.

Built on top of **DOM Testing Library** and commonly used with **Jest/Vitest**.

### Core philosophy

> Test what the user can see and do, not implementation details.

❌ Avoid:

```js
expect(component.state.count).toBe(1);
```

✅ Prefer:

```js
expect(screen.getByText('Count: 1')).toBeInTheDocument();
```

### Why RTL?

* Encourages user-centric tests
* Less coupled to component implementation
* Works well with accessibility
* Easy refactoring without breaking tests
* Supports synchronous and asynchronous UI

# 2. Basic Setup

Typical imports:

```js
import { render, screen } from '@testing-library/react';
import '@testing-library/jest-dom';
```

For interactions:

```js
import userEvent from '@testing-library/user-event';
```

Example component:

```jsx
function Greeting() {
  return <h1>Hello World</h1>;
}
```

Test:

```jsx
test('renders greeting', () => {
  render(<Greeting />);

  expect(
    screen.getByRole('heading', { name: /hello world/i })
  ).toBeInTheDocument();
});
```

# 3. `render()`

Renders a React component into a test DOM.

```js
render(<User />);
```

You can render with props:

```js
render(<User name="John" />);
```

### With Provider

Very common in real projects:

```jsx
render(
  <Provider store={store}>
    <User />
  </Provider>
);
```

Instead of repeating providers, create a custom render:

```jsx
const renderWithProviders = (ui) => {
  return render(
    <Provider store={store}>
      {ui}
    </Provider>
  );
};
```

---

# 4. `screen`

`screen` provides access to the rendered DOM.

```js
screen.getByRole(...)
screen.getByText(...)
screen.getByLabelText(...)
```

Prefer `screen` over destructuring queries from `render()`.

❌

```js
const { getByText } = render(<App />);
```

✅

```js
render(<App />);
screen.getByText('Hello');
```

---

# 5. RTL Queries ⭐

This is one of the **most important interview topics**.

### Query priority

Generally prefer:

1. `getByRole`
2. `getByLabelText`
3. `getByPlaceholderText`
4. `getByText`
5. `getByDisplayValue`
6. `getByAltText`
7. `getByTitle`
8. `getByTestId`

---

## `getByRole()` ⭐⭐⭐

Preferred query because it closely represents accessibility/user interaction.

```jsx
<button>Submit</button>
```

```js
screen.getByRole('button', { name: /submit/i });
```

Input:

```jsx
<input aria-label="Username" />
```

```js
screen.getByRole('textbox', { name: /username/i });
```

Other roles:

```js
getByRole('button')
getByRole('heading')
getByRole('textbox')
getByRole('checkbox')
getByRole('radio')
getByRole('link')
getByRole('list')
```

---

# 6. `getByLabelText()`

Best for form fields.

```jsx
<label htmlFor="email">Email</label>
<input id="email" />
```

```js
screen.getByLabelText('Email');
```

This also encourages accessible forms.

---

# 7. `getByText()`

Finds visible text.

```jsx
<p>Welcome John</p>
```

```js
screen.getByText('Welcome John');
```

Regex is useful:

```js
screen.getByText(/welcome john/i);
```

---

# 8. `getByTestId()`

Use when there isn't a good semantic query.

```jsx
<div data-testid="user-profile">
  John
</div>
```

```js
screen.getByTestId('user-profile');
```

### Interview point

`data-testid` should generally be a **fallback**, not your first choice.

---

# 9. `getBy*` vs `queryBy*` vs `findBy*` ⭐⭐⭐

Very important.

| Query     | Use case                         | Failure        |
| --------- | -------------------------------- | -------------- |
| `getBy`   | Element should exist immediately | Throws         |
| `queryBy` | Element may not exist            | Returns `null` |
| `findBy`  | Element appears asynchronously   | Promise        |

### `getBy`

```js
expect(screen.getByText('Welcome')).toBeInTheDocument();
```

If missing → test fails immediately.

### `queryBy`

Useful for asserting something **doesn't exist**:

```js
expect(screen.queryByText('Loading...')).not.toBeInTheDocument();
```

### `findBy`

For async UI:

```js
expect(
  await screen.findByText('User loaded')
).toBeInTheDocument();
```

---

# 10. `findBy` vs `waitFor` ⭐

### `findBy`

Use when waiting for **one element**.

```js
const user = await screen.findByText('John');

expect(user).toBeInTheDocument();
```

### `waitFor`

Use when waiting for an **arbitrary assertion/state change**.

```js
await waitFor(() => {
  expect(mockApi).toHaveBeenCalled();
});
```

Import:

```js
import { waitFor } from '@testing-library/react';
```

### Don't do this unnecessarily

```js
await waitFor(() => {
  expect(screen.getByText('John')).toBeInTheDocument();
});
```

Prefer:

```js
await screen.findByText('John');
```

---

# 11. `userEvent` ⭐⭐⭐

Use `userEvent` to simulate realistic user interactions.

```js
const user = userEvent.setup();

await user.click(button);
await user.type(input, 'John');
await user.clear(input);
await user.selectOptions(select, 'India');
```

Example:

```jsx
test('user enters email', async () => {
  const user = userEvent.setup();

  render(<Login />);

  const input = screen.getByLabelText(/email/i);

  await user.type(input, 'john@test.com');

  expect(input).toHaveValue('john@test.com');
});
```

### `userEvent` vs `fireEvent`

`fireEvent` triggers DOM events directly.

```js
fireEvent.click(button);
```

`userEvent` simulates a more realistic user interaction.

**Prefer `userEvent` for most application tests.**

# 12. Testing Form Submission

Component:

```jsx
function Login() {
  const handleSubmit = jest.fn();

  return (
    <form onSubmit={handleSubmit}>
      <label htmlFor="email">Email</label>
      <input id="email" />

      <button type="submit">Login</button>
    </form>
  );
}
```

Test:

```js
test('submits form', async () => {
  const user = userEvent.setup();

  render(<Login />);

  await user.type(
    screen.getByLabelText(/email/i),
    'john@test.com'
  );

  await user.click(
    screen.getByRole('button', { name: /login/i })
  );

  // assertions...
});
```

# 14. Testing Conditional Rendering

Component:

```jsx
function Status({ loading }) {
  return loading
    ? <p>Loading...</p>
    : <p>Loaded</p>;
}
```

Test:

```js
test('shows loading state', () => {
  render(<Status loading={true} />);

  expect(screen.getByText('Loading...'))
    .toBeInTheDocument();

  expect(screen.queryByText('Loaded'))
    .not.toBeInTheDocument();
});
```

# 15. Testing Async API Calls ⭐⭐⭐

Example:

```jsx
function User() {
  const [user, setUser] = useState(null);

  useEffect(() => {
    fetch('/api/user')
      .then(res => res.json())
      .then(data => setUser(data));
  }, []);

  if (!user) return <p>Loading...</p>;

  return <p>{user.name}</p>;
}
```

Test:

```js
test('loads user', async () => {
  render(<User />);

  expect(screen.getByText('Loading...'))
    .toBeInTheDocument();

  expect(
    await screen.findByText('John')
  ).toBeInTheDocument();
});
```

---

# 16. Mocking API Calls ⭐⭐⭐

A common approach is **MSW (Mock Service Worker)**.

Conceptually:

```text
Component
   ↓
fetch('/api/user')
   ↓
MSW intercepts request
   ↓
Mock response
   ↓
Component renders data
```

Example:

```js
http.get('/api/user', () => {
  return HttpResponse.json({
    id: 1,
    name: 'John'
  });
});
```

This is generally preferable to deeply mocking `fetch` because it tests the application closer to real behavior.

---

# 17. Testing Error State

```jsx
if (error) {
  return <p>Something went wrong</p>;
}
```

Test:

```js
expect(
  await screen.findByText(/something went wrong/i)
).toBeInTheDocument();
```

Important scenarios:

```text
Loading
   ↓
Success

Loading
   ↓
Error

Loading
   ↓
Empty state
```

Always consider these states for API-driven components.

# 18. Mock Functions

Jest:

```js
const mockFn = jest.fn();
```

Check invocation:

```js
expect(mockFn).toHaveBeenCalled();
```

Specific arguments:

```js
expect(mockFn).toHaveBeenCalledWith('John');
```

Call count:

```js
expect(mockFn).toHaveBeenCalledTimes(1);
```

---

# 19. Mocking Modules

Example:

```js
jest.mock('./api', () => ({
  getUser: jest.fn()
}));
```

Then:

```js
getUser.mockResolvedValue({
  id: 1,
  name: 'John'
});
```

### Important

Don't mock everything.

Mock **external boundaries** such as:

* APIs
* browser APIs
* third-party integrations

Avoid mocking internal implementation unnecessarily.

# 20. Testing React Router

Wrap component with router:

```jsx
render(
  <MemoryRouter initialEntries={['/users']}>
    <User />
  </MemoryRouter>
);
```

Test navigation:

```js
const user = userEvent.setup();

await user.click(
  screen.getByRole('link', { name: /profile/i })
);

expect(
  await screen.findByText(/profile/i)
).toBeInTheDocument();
```

`MemoryRouter` is particularly useful in tests because it keeps routing state in memory.

---

# 21. Testing Redux Components ⭐⭐⭐

Provide the Redux store.

```jsx
render(
  <Provider store={store}>
    <User />
  </Provider>
);
```

Better:

```jsx
const renderWithProviders = (
  ui,
  { preloadedState } = {}
) => {
  const store = configureStore({
    reducer,
    preloadedState
  });

  return render(
    <Provider store={store}>
      {ui}
    </Provider>
  );
};
```

Then:

```js
renderWithProviders(<User />, {
  preloadedState: {
    user: {
      name: 'John'
    }
  }
});
```

### Key principle

Test Redux through **user-visible behavior**, not by testing implementation details of reducers/store inside every component test.

Create a provider:

```jsx
render(
  <AuthContext.Provider value={{ user: 'John' }}>
```

# 23. `act()` ⭐

React uses `act()` to ensure updates are processed before assertions.

Usually RTL handles `act()` automatically:

```js
await user.click(button);
```

So you generally **shouldn't manually wrap normal RTL interactions with `act()`**.

---

# 24. `cleanup`

RTL automatically cleans up rendered components in modern setups.

You generally don't need:

```js
afterEach(cleanup);
```

unless your test environment/setup specifically requires it.

---

# 25. Testing Hooks

For custom hooks, modern RTL provides `renderHook`.

```js
import { renderHook, act } from '@testing-library/react';

const { result } = renderHook(() => useCounter());

expect(result.current.count).toBe(0);

act(() => {
  result.current.increment();
});

expect(result.current.count).toBe(1);
```

### But important

If a hook is only meaningful through a component, testing the **component behavior** is often more valuable than testing the hook implementation directly.

---

# 26. Testing Accessibility ⭐⭐⭐

RTL encourages accessible applications.

Prefer:

```js
screen.getByRole('button', { name: /submit/i });
```

instead of:

```js
screen.getByTestId('submit-button');
```

You can also use:

```js
expect(button).toBeEnabled();
```

Accessibility tests can be supplemented with tools such as `jest-axe`.

---

# 27. Snapshot Testing

Example:

```js
expect(container).toMatchSnapshot();
```

Snapshot stores rendered output.

### Advantages

* Detect unexpected UI changes
* Easy for stable/simple structures

### Disadvantages

* Large snapshots become difficult to review
* Developers may blindly update snapshots
* Can test implementation details

**Don't use snapshots as the primary testing strategy.**

Prefer behavior assertions:

```js
expect(screen.getByRole('button')).toBeInTheDocument();
```

---

# 28. `beforeEach`, `afterEach`

Common setup:

```js
beforeEach(() => {
  jest.clearAllMocks();
});
```

Cleanup:

```js
afterEach(() => {
  // cleanup if required
});
```

Know the difference:

```js
jest.clearAllMocks();
```

Clears call history.

```js
jest.resetAllMocks();
```

Resets mock implementations too.

```js
jest.restoreAllMocks();
```

Restores original implementations for spies.

# 32. Common RTL Mistakes ⭐⭐⭐

### ❌ Testing implementation details

```js
expect(component.state).toEqual(...);
```

### ✅ Test behavior

```js
expect(screen.getByText('Success')).toBeInTheDocument();
```

---

### ❌ Using `getBy` for absence

```js
expect(screen.getByText('Error')).not.toBeInTheDocument();
```

This throws before the assertion.

### ✅

```js
expect(screen.queryByText('Error')).not.toBeInTheDocument();
```

---

### ❌ Using `waitFor` everywhere

```js
await waitFor(() =>
  expect(screen.getByText('John')).toBeInTheDocument()
);
```

### ✅

```js
expect(await screen.findByText('John'))
  .toBeInTheDocument();
```

---

### ❌ Overusing `data-testid`

```js
screen.getByTestId('submit');
```

### ✅

```js
screen.getByRole('button', { name: /submit/i });
```

---

### ❌ Using arbitrary delays

```js
await new Promise(resolve => setTimeout(resolve, 1000));
```

### ✅

Use RTL async queries:

```js
await screen.findByText('Loaded');
```

# 33. Testing Strategy

For a real React application:

```text
              Tests
                │
       ┌────────┼─────────┐
       ↓        ↓         ↓
     Unit    Integration   E2E
       │        │          │
     Hooks    Components   Full app
     Utils    Redux/API    Browser
```

RTL is primarily excellent for **component and integration-style UI tests**.


### User interaction

```text
✓ Click
✓ Type
✓ Select

```

### State


### Integration

```text

✓ Redux
```


# 35. Real-World Example ⭐⭐⭐

```jsx
function Login() {
  const [loading, setLoading] = useState(false);

  const handleSubmit = async () => {
    setLoading(true);

    await login();

    setLoading(false);
  };

  return (
    <>
      <label htmlFor="email">Email</label>

      <input id="email" />

      <button
        onClick={handleSubmit}
        disabled={loading}
      >
        {loading ? 'Logging in...' : 'Login'}
      </button>
    </>
  );
}
```

Test:

```js
test('login flow', async () => {
  const user = userEvent.setup();

  render(<Login />);

  const email = screen.getByLabelText(/email/i);
  const button = screen.getByRole('button', {
    name: /login/i
  });

  await user.type(email, 'john@test.com');
  await user.click(button);

  expect(
    screen.getByRole('button', {
      name: /logging in/i
    })
  ).toBeDisabled();
});
```

This test verifies **what the user experiences**, rather than checking internal state.

# 36. RTL Query Cheat Sheet ⭐

```text
getByRole()             → preferred
getByLabelText()        → forms
getByText()             → visible text
getByPlaceholderText()  → placeholder
getByAltText()          → images
getByDisplayValue()     → input current value
getByTestId()           → last resort
```

Async:

```text
findBy*     → wait for element
waitFor()   → wait for assertion/state
```

Absence:

```text
queryBy*    → element may not exist
```

# 37. Most Important Interview Questions ⭐⭐⭐

### Q1. What is RTL?

A testing library that encourages testing React components from the user's perspective rather than testing implementation details.

### Q2. `getBy` vs `queryBy` vs `findBy`?

```text
getBy    → synchronous + must exist
queryBy  → synchronous + may not exist
findBy   → asynchronous + waits
```

### Q3. `userEvent` vs `fireEvent`?

`userEvent` simulates realistic user interactions; `fireEvent` directly dispatches DOM events.

### Q4. What query should you prefer?

```js
getByRole()
```

because it encourages accessible, user-centric tests.

### Q5. When use `waitFor()`?

When waiting for an arbitrary asynchronous assertion or state change.

### Q6. Why avoid implementation-detail testing?

Tests become tightly coupled to component internals and break during harmless refactoring.

### Q7. How do you test API calls?

Prefer mocking the network boundary, commonly with **MSW**, then assert the resulting UI.

### Q8. How do you test Redux?

Render the component with a real test store/provider and verify user-visible behavior.

### Q9. Why use `queryBy` for negative assertions?

Because `getBy` throws when the element isn't found.

### Q10. Should every element have `data-testid`?

**No.** Prefer semantic/accessibility-based queries and use test IDs when no suitable user-facing selector exists.

## ⭐ Senior-Level Mental Model

Think of RTL testing as:

```text
          USER
           │
      ┌────▼────┐
      │   UI    │
      └────┬────┘
           │
    User interactions
           │
      ┌────▼────┐
      │  State  │
      └────┬────┘
           │
       API / Redux
           │
      ┌────▼────┐
      │   UI    │
      └─────────┘
```

**Arrange → Act → Assert**

```js
// Arrange
render(<Login />);

// Act
await user.click(loginButton);

// Assert
expect(screen.getByText('Success')).toBeInTheDocument();
```

### Golden rule

> **Don't test how the component works. Test what the user can observe and do.**

For a **5-year React developer**, the highest-priority RTL topics to master are **`getByRole`, query selection, `getBy/queryBy/findBy`, `userEvent`, async testing, MSW/API mocking, Redux/Router/Context integration, accessibility, and avoiding implementation-detail tests**.
