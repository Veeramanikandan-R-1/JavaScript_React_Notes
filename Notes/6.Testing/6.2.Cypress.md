# React JS — Cypress Notes

For a **5-year React developer**, think of Cypress primarily as an **E2E/component testing tool** that validates your application from the browser/user perspective.

---

## 1. What is Cypress?

**Cypress** is a JavaScript-based testing framework mainly used for:

* E2E testing
* Component testing
* API testing
* UI automation
* Regression testing

Unlike RTL, Cypress runs tests in a **real browser environment** and is especially useful for testing complete user flows.

### RTL vs Cypress

| RTL                             | Cypress                              |
| ------------------------------- | ------------------------------------ |
| Component/integration testing   | E2E + component testing              |
| Tests UI behavior               | Tests real browser flows             |
| JSDOM environment commonly used | Real browser                         |
| Faster                          | Generally slower                     |
| Great for isolated components   | Great for complete application flows |

Typical strategy:

```text
Unit/Component → RTL
Integration     → RTL + Cypress
E2E             → Cypress
```

# 4. Basic Test Structure ⭐

```js
describe('Login', () => {

  it('should login successfully', () => {

    cy.visit('/login');

    cy.get('[data-testid="email"]')
      .type('john@test.com');

    cy.get('[data-testid="password"]')
      .type('password');

    cy.get('[data-testid="login"]')
      .click();

    cy.contains('Dashboard')
      .should('be.visible');
  });

});
```

### Structure

```text
describe()
   └── it()
         ├── Arrange
         ├── Act
         └── Assert
```

# 5. `cy.visit()`

Navigates to a URL.

```js
cy.visit('/login');
```

```js

```

Usually configure `baseUrl`:

```js
// cypress.config.js

export default defineConfig({
  e2e: {
    baseUrl: 'http://localhost:3000'
  }
});
```

Then:

```js

```

# 7. `cy.get()` vs `cy.contains()` ⭐

### `cy.get()`

Finds elements using a selector.

```js
cy.get('[data-testid="submit"]');
```

### `cy.contains()`

Finds an element containing text.

```js
cy.contains('Submit');
```

Can combine:

```js
cy.get('button').contains('Submit');
```

# 8. Assertions ⭐⭐⭐

Cypress uses Chai-style assertions.

```js
cy.get('h1')
  .should('be.visible');
```

Common assertions:

```js
.should('exist');

.should('not.exist');

.should('be.visible');

.should('not.be.visible');

.should('be.enabled');

.should('be.disabled');

.should('have.text', 'Login');

.should('contain.text', 'Welcome');

.should('have.value', 'John');

.should('have.attr', 'href', '/home');

.should('have.class', 'active');
```

---

# 9. `.should()` vs `.then()` ⭐⭐⭐

### `.should()`

Cypress automatically retries assertions.

```js
cy.get('[data-testid="user"]')
  .should('be.visible');
```

If the element takes time to appear, Cypress retries until timeout.

### `.then()`

Used when you need to work with the resolved subject.

```js
cy.get('[data-testid="username"]')
  .then(($el) => {
    const text = $el.text();

    expect(text).to.equal('John');
  });
```

### Key difference

```text
.should() → assertion + automatic retry
.then()   → execute callback after subject resolves
```

# 10. Automatic Waiting ⭐⭐⭐

One of Cypress's biggest advantages.

You generally don't need:

```js
cy.wait(5000);
```

❌ Avoid arbitrary waits.

Instead:

```js
cy.get('[data-testid="dashboard"]')
  .should('be.visible');
```

Cypress automatically retries commands/assertions until timeout.

---

# 11. `cy.wait()`

### Waiting for an alias

Preferred:

```js
cy.intercept('GET', '/api/users')
  .as('getUsers');

cy.visit('/users');

cy.wait('@getUsers');
```

Then:

```js
cy.wait('@getUsers')
  .its('response.statusCode')
  .should('eq', 200);
```

### Avoid

```js
cy.wait(3000);
```

unless there is a genuine reason.

# 13. `{ force: true }` ⭐

Normally Cypress interacts only with elements it considers actionable/visible.

```js
cy.get('#submit').click();
```

If an element is covered/hidden:

```js
cy.get('#submit').click({ force: true });
```

### Important

Don't use `force: true` as the default solution.

It can hide genuine UI problems such as:

* Element covered
* Incorrect layout
* `display: none`
* `overflow: hidden`
* Wrong selector

Use it only when the behavior is intentionally valid.

# 16. API Mocking with `cy.intercept()` ⭐⭐⭐

One of the most important Cypress concepts.

```js
cy.intercept('GET', '/api/users', {
  statusCode: 200,
  body: [
    { id: 1, name: 'John' }
  ]
}).as('getUsers');
```

Then:

```js
cy.visit('/users');

cy.wait('@getUsers');

cy.contains('John')
  .should('be.visible');
```

### Why?

You can test UI independently from a real backend.

# 17. Mock API Error

```js
cy.intercept('GET', '/api/users', {
  statusCode: 500,
  body: {
    message: 'Server error'
  }
}).as('getUsers');
```

Then:

```js
cy.visit('/users');

cy.wait('@getUsers');

  .should('be.visible');
```

This makes testing error scenarios easy.

# 18. Inspect API Request/Response

```js
cy.intercept('POST', '/api/login')
  .as('login');

cy.get('[data-testid="login"]')
  .click();

cy.wait('@login')
  .its('response.statusCode')
  .should('eq', 200);
```

You can inspect:

```js
cy.wait('@login')
  .then((interception) => {
    console.log(interception.request.body);
    console.log(interception.response.body);
  });
```

# 19. Custom Commands ⭐⭐⭐

Create reusable commands in:

```text
cypress/support/commands.js
```

Example:

```js
Cypress.Commands.add('login', (email, password) => {
  cy.get('[data-testid="email"]').type(email);
  cy.get('[data-testid="password"]').type(password);
  cy.get('[data-testid="login"]').click();
});
```

Use:

```js
cy.login('john@test.com', 'password');
```

### Good candidates

* Login
* Logout
* Common navigation
* Reusable setup

Don't put complex test logic into custom commands just to make tests shorter.

# 20. Authentication ⭐⭐⭐

Avoid logging in through the UI for **every test**.

Use:

```js
cy.session()
```

Example:

```js
Cypress.Commands.add('login', () => {
  cy.session('user', () => {
    cy.request('POST', '/api/login', {
      email: 'john@test.com',
      password: 'password'
    });
  });
});
```

Then:

```js
beforeEach(() => {
  cy.login();
});
```

### Benefit

* Faster tests
* Less duplication
* More stable test suite

# 23. Hooks ⭐

### `before`

Runs once before all tests.

```js
before(() => {
  // setup
});
```

### `beforeEach`

Runs before every test.

```js

  cy.visit('/login');
});
```

### `afterEach`

Runs after every test.

```js
afterEach(() => {
  // cleanup
});
```

### `after`

Runs once after all tests.

# 25. Cypress Command Chaining ⭐⭐⭐

Cypress commands are chainable:

```js
cy.get('[data-testid="user"]')
  .should('be.visible')
  .and('contain.text', 'John');
```

Another example:

```js
cy.get('form')
  .find('input')
  .first()
  .type('John');
```

# 26. Cypress is Asynchronous

This is a common interview question.

❌ Don't treat Cypress commands like normal synchronous JavaScript:

```js
const value = cy.get('input');
```

Cypress commands are **queued** and executed by Cypress.

Instead:

```js
cy.get('input')
  .invoke('val')
  .then((value) => {
    console.log(value);
  });
```

# 32. Test Isolation

Each test should ideally be independent.

❌ Avoid:

```text
Test 1 creates user
      ↓
Test 2 depends on user from Test 1
```

Prefer:

```text
Test 1 → setup → test → cleanup
Test 2 → setup → test → cleanup
```

This prevents cascading failures.

# 33. Page Object Model

You may see POM in Cypress projects.

Example:

```js
class LoginPage {
  email() {
    return cy.get('[data-testid="email"]');
  }

  password() {
    return cy.get('[data-testid="password"]');
  }

  login() {
    return cy.get('[data-testid="login"]');
  }
}

export default new LoginPage();
```

Usage:

```js
LoginPage.email().type('john@test.com');
LoginPage.password().type('password');
LoginPage.login().click();
```

### But don't over-engineer

For smaller applications, simple custom commands and reusable functions can be cleaner than a large POM hierarchy.

# 34. Retry-ability ⭐⭐⭐

Cypress automatically retries many commands/assertions.

```js
cy.get('[data-testid="result"]')
  .should('contain.text', 'Success');
```

If the element isn't ready immediately, Cypress retries until the command timeout.

This is one of Cypress's major differences from traditional WebDriver-based automation.

# 35. Common Mistakes ⭐⭐⭐

### ❌ Arbitrary waits

```js
cy.wait(5000);
```

### ✅ Wait for actual condition

```js
cy.get('[data-testid="result"]')
  .should('be.visible');
```

---

### ❌ Fragile selectors

```js
cy.get('.css-class-123');
```

### ✅ Stable selector

```js
cy.get('[data-testid="submit"]');
```

---

### ❌ Testing implementation details

Don't assert React internals.

❌

```js
expect(component.state(...));
```

### ✅

```js
cy.contains('Success')
  .should('be.visible');
```

---

### ❌ Overusing `force`

```js
cy.get('button').click({ force: true });
```

Use only when justified.

---

### ❌ Making tests dependent on each other

Each test should be independently executable.

# 36. Real-World React Login Test ⭐⭐⭐

```js
describe('Login flow', () => {

  beforeEach(() => {
    cy.visit('/login');
  });

  it('logs in successfully', () => {

    cy.intercept('POST', '/api/login', {
      statusCode: 200,
      body: {
        token: 'fake-token'
      }
    }).as('login');

    cy.get('[data-testid="email"]')
      .type('john@test.com');

    cy.get('[data-testid="password"]')
      .type('password');

    cy.get('[data-testid="login"]')
      .click();

    cy.wait('@login')
      .its('response.statusCode')
      .should('eq', 200);

    cy.url()
      .should('include', '/dashboard');

    cy.contains('Dashboard')
      .should('be.visible');
  });

});
```

This covers:

```text
Visit
 ↓
Input
 ↓
Click
 ↓
API interception
 ↓
API assertion
 ↓
Navigation
 ↓
UI assertion
```

# 37. Recommended Cypress Test Pyramid

For a React application:

```text
             ┌───────────┐
             │   E2E     │  ← Cypress
             │  Few      │
             ├───────────┤
             │Integration│  ← RTL/Cypress
             │  Medium   │
             ├───────────┤
             │ Component │  ← RTL
             │   Many    │
             └───────────┘
```

Don't write every possible scenario as E2E tests—they are slower and more expensive to maintain.

# 38. Senior-Level Best Practices ⭐⭐⭐

```text
✓ Test user behavior, not implementation
✓ Prefer stable selectors
✓ Prefer semantic/accessibility selectors where practical
✓ Use cy.intercept() for network control
✓ Avoid arbitrary cy.wait(milliseconds)
✓ Use aliases for important requests
✓ Keep tests independent
✓ Use cy.session() for reusable authentication
✓ Use fixtures for reusable static data
✓ Use custom commands for common workflows
✓ Keep E2E tests focused on critical business flows
✓ Run tests in CI/CD
✓ Capture screenshots/videos for failures
✓ Don't use force:true unnecessarily
✓ Don't overuse Page Objects
```
