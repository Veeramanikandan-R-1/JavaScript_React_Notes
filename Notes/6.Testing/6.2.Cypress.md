# Cypress (Basics)

## What is Cypress?

Cypress is an **End-to-End (E2E) testing framework** used to test web applications by simulating how a real user interacts with the application.

Instead of testing individual functions, Cypress tests the complete application flow.

**Examples**

* Login flow
* Create/Edit/Delete user
* Checkout flow
* Navigation between pages
* Form validation

---

## Why Cypress?

* Easy setup
* Runs inside the browser
* Automatic waiting (no need for explicit sleeps)
* Time travel debugging
* Screenshots & videos on failure
* Great developer experience

---

## Types of Testing in Cypress

### 1. E2E Testing (Most Common)

Tests the entire application flow.

```
Login
   ↓
Dashboard
   ↓
Create User
   ↓
Logout
```

Example

```
Visit login page
Enter username/password
Click Login
Verify Dashboard appears
```

---

### 2. Component Testing

Tests a single React component.

```
<Button />
<LoginForm />
<UserCard />
```

Less common compared to React Testing Library.

# Test Structure

```javascript
describe('Login', () => {

  it('should login successfully', () => {

    cy.visit('/login');

    cy.get('#email')
      .type('admin@test.com');

    cy.get('#password')
      .type('123456');

    cy.get('button')
      .click();

    cy.contains('Dashboard');

  });

});
```

# Automatic Waiting

One of Cypress' biggest advantages.

Instead of

```javascript
setTimeout(...)
```

Cypress automatically waits until the element appears.

```javascript
cy.get('.loader')
```

It retries until timeout.

Avoid

```javascript
cy.wait(5000)
```

Use only when absolutely necessary.

# API Mocking in Cypress

## What is API Mocking?

Instead of calling the real backend, Cypress can return a fake response.

```
Frontend
     ↓
 Cypress Intercepts
     ↓
Fake Response
```

Benefits

* Faster tests
* No backend dependency
* Test edge cases easily
* Stable CI builds

---

## cy.intercept()

Used to intercept API requests.

```javascript
cy.intercept('GET', '/api/users');
```

---

## Mock API Response

```javascript
cy.intercept('GET', '/api/users', {
    statusCode:200,
    body:[
      {
        id:1,
        name:'John'
      }
    ]
});
```

Now the frontend receives the mocked response instead of hitting the real API.

---

## Mock using Fixture

```
fixtures/users.json
```

```json
[
  {
    "id":1,
    "name":"John"
  }
]
```

```javascript
cy.intercept(
    'GET',
    '/api/users',
    { fixture:'users.json' }
);
```

This is the preferred approach because test data stays separate from the test code.

---

## Alias Requests

```javascript
cy.intercept('GET','/api/users')
  .as('getUsers');

cy.visit('/users');

cy.wait('@getUsers');
```

Useful when you need to wait for an API before making assertions.

---

## Verify Request

```javascript
cy.wait('@getUsers')
  .its('response.statusCode')
  .should('eq',200);
```

---

## Mock Error Response

Test error handling without changing the backend.

```javascript
cy.intercept('GET','/api/users',{
    statusCode:500,
    body:{
       message:'Server Error'
    }
});
```

Verify the UI shows an error message.

---

## Mock Delay

Useful for testing loading spinners.

```javascript
cy.intercept('GET','/api/users', {
    delay:3000,
    body:[]
});
```

Check:

* Loader appears
* Loader disappears after response
* Data renders correctly

---

## Modify Existing Response

```javascript
cy.intercept('GET', '/api/users', (req) => {
  req.reply((res) => {
    res.body.push({
      id: 100,
      name: 'Mock User'
    });
  });
});
```

This allows you to inspect or modify the response before it's returned to the application.

# Real Backend vs Mocked Backend

| Real API                        | Mock API              |
| ------------------------------- | --------------------- |
| Tests backend + frontend        | Tests frontend only   |
| Can be slow                     | Very fast             |
| Depends on backend availability | Independent           |
| Data may change                 | Predictable           |
| Good for integration tests      | Good for UI/E2E tests |

**Interview Tip:** A balanced test suite usually includes both:

* **Mocked API tests** for fast, reliable UI validation.
* **Real API tests** for end-to-end integration confidence.

# Common Mistakes

❌ Using `cy.wait(5000)` everywhere.

❌ Selecting elements with fragile CSS selectors.

❌ Depending on production APIs.

❌ Writing one huge test for the entire application.

❌ Sharing state between tests.

❌ Hardcoding test data inside test files.

# Revision Notes (5-Min Cheat Sheet)

### Cypress

* End-to-End testing framework
* Runs inside browser
* Automatic waiting
* Uses `describe()` and `it()`
* `cy.visit()` → open page
* `cy.get()` → find element
* `.type()` → type text
* `.click()` → click
* `.should()` → assertions
* `beforeEach()` → setup before every test
* Fixtures store reusable JSON
* Custom commands avoid duplicate code
* Prefer `data-testid` selectors
* Avoid `cy.wait()` unless required

### API Mocking

* `cy.intercept()` intercepts HTTP requests
* Mock success, error, and delayed responses
* Use fixture files for mock data
* `.as()` creates request aliases
* `cy.wait('@alias')` waits for and inspects requests
* Mock APIs make tests faster and more reliable

# Common React Interview Questions (6 Years Experience)

### 1. Why is Cypress preferred over Selenium?

**Answer:** Cypress runs directly in the browser, provides automatic waiting, faster execution, time-travel debugging, and doesn't require a separate WebDriver.

---

### 2. What is `cy.intercept()`?

**Answer:** It intercepts HTTP requests, allowing you to mock, modify, or verify network traffic during tests.

---

### 3. When should you mock APIs instead of calling real APIs?

**Answer:** Mock APIs for fast, deterministic UI tests. Use real APIs for integration and end-to-end validation.

---

### 4. Why should `cy.wait(5000)` be avoided?

**Answer:** Fixed waits slow tests and make them flaky. Cypress automatically retries commands until elements or requests are ready.

---

### 5. Why use `data-testid` selectors?

**Answer:** They are stable and unaffected by styling or layout changes, making tests less brittle.

---

### 6. How do you wait for an API call in Cypress?

```javascript
cy.intercept('GET', '/api/users').as('getUsers');

cy.visit('/users');

cy.wait('@getUsers');
```

---

### 7. How do you test loading and error states?

**Answer:** Mock delayed responses to verify loaders and mock error responses (e.g., 500 status) to verify error handling.

---

### 8. Where do you place reusable Cypress commands?

**Answer:** In `cypress/support/commands.js`, then invoke them using `cy.<commandName>()`.

---

### 9. What is the difference between fixtures and mocks?

**Answer:** Fixtures are static JSON files containing test data. Mocks use that data (or inline data) to simulate API responses, typically with `cy.intercept()`.

---

### 10. What testing strategy would you follow in a React project?

**Answer:** Use:

* **Unit tests** (React Testing Library) for components and hooks.
* **Integration tests** for feature workflows.
* **Cypress E2E tests** for critical user journeys such as login, checkout, and CRUD operations.
