# JavaScript Memory — Interview Notes

JavaScript memory is mainly managed automatically by the JS engine. The key concepts are **Stack, Heap, and Garbage Collection**.

---

## 1. Stack ⭐⭐⭐

The **Call Stack** stores execution contexts and typically holds **primitive values and references to objects**.

```js
let age = 30;
let name = "John";

function add(a, b) {
  return a + b;
}
```

Conceptually:

```text
Stack
┌──────────────┐
│ add()        │
│ a = 10       │
│ b = 20       │
├──────────────┤
│ global       │
│ age = 30     │
│ name → Heap  │
└──────────────┘
```

### Key point

Don't oversimplify this as:

> "Primitive = Stack, Object = Heap."

The exact memory representation is **engine-dependent**. For interviews, it's better to say:

> **Stack is used for function execution state and commonly stores primitive values/references, while objects are generally allocated in the heap.**

---

# 2. Heap ⭐⭐⭐

The **Heap** is a larger memory area where objects, arrays, and functions are generally allocated.

```js
const user = {
  name: "John",
  age: 30
};

const numbers = [1, 2, 3];
```

Conceptually:

```text
Stack                 Heap
┌──────────┐          ┌─────────────────┐
│ user ─────────────→ │ { name: "John" }│
│ numbers ──────────→ │ [1, 2, 3]       │
└──────────┘          └─────────────────┘
```

The variable `user` holds a **reference** to the object.

### Reference behavior ⭐

```js
const user1 = { name: "John" };
const user2 = user1;

user2.name = "Bob";

console.log(user1.name);
// "Bob"
```

Both variables reference the **same object**.

---

# 3. Garbage Collection ⭐⭐⭐

JavaScript automatically removes memory that is **no longer reachable**.

This process is called **Garbage Collection (GC)**.

You don't normally manually free memory.

### Example

```js
let user = {
  name: "John"
};

user = null;
```

Now the original object has no reference pointing to it, so it becomes **eligible for garbage collection**.

```text
Before:

user ─────→ { name: "John" }


After:

user ─────→ null

{ name: "John" }  ← unreachable
                  ↓
             GC can clean it
```

⚠️ "Eligible" does not mean it is immediately deleted. The JavaScript engine decides when GC runs.

---

# ⭐ Reachability

Modern JavaScript garbage collectors are generally based on **reachability**.

An object is considered alive if it can still be reached from **GC roots**, such as active execution contexts/global references.

```js
let user = {
  name: "John"
};

let admin = user;

user = null;
```

The object is **still reachable**:

```text
admin ─────→ { name: "John" }
```

So it cannot be garbage collected.

If:

```js
admin = null;
```

and there are no other references, the object becomes unreachable.

---

# ⚠️ Memory Leak ⭐⭐⭐

A **memory leak** happens when memory is no longer logically needed but remains reachable, preventing garbage collection.

Common causes:

### 1. Uncleared timers

```js
const id = setInterval(() => {
  // work
}, 1000);

// Cleanup when no longer needed
clearInterval(id);
```

### 2. Event listeners not removed

Especially important in React:

```js
useEffect(() => {
  const handler = () => console.log("resize");

  window.addEventListener("resize", handler);

  return () => {
    window.removeEventListener("resize", handler);
  };
}, []);
```

### 3. Unnecessary references

```js
const cache = [];

function addData(data) {
  cache.push(data);
}
```

If `cache` continuously grows without cleanup, memory usage can grow.

---

# ⭐ Stack Overflow vs Heap Out of Memory

### Stack Overflow

Usually caused by excessive recursion:

```js
function test() {
  test();
}

test();
// RangeError: Maximum call stack size exceeded
```

### Heap Out of Memory

Usually caused by excessive memory allocation or retained objects.

```js
const hugeArray = [];

while (true) {
  hugeArray.push(new Array(1000000));
}
```

Eventually the process can run out of heap memory.

# 🎯 React Interview Connection

Memory management matters in React mainly around:

* `useEffect` cleanup
* Event listeners
* Timers
* Subscriptions
* WebSockets
* Large caches
* Unnecessary object/array retention

Example:

```jsx
useEffect(() => {
  const timer = setInterval(() => {
    console.log("running");
  }, 1000);

  return () => {
    clearInterval(timer);
  };
}, []);
```

Cleanup prevents the timer from continuing after the component is unmounted.

# ⭐ Quick Revision

```text
Stack
→ Function execution / call stack
→ Primitive values and references are commonly represented here

Heap
→ Objects, arrays, functions are generally allocated here

Garbage Collection
→ Automatically reclaims unreachable memory

Reachability
→ If an object is reachable, GC cannot remove it

Memory Leak
→ Unneeded memory remains reachable

Stack Overflow
→ Call stack exhausted, commonly infinite recursion

Heap OOM
→ Available heap memory exhausted
```

### ⭐ Interview One-Liner

> **JavaScript automatically manages memory: execution state is handled through the stack, objects are generally allocated in the heap, and garbage collection reclaims objects that are no longer reachable.**

---

Note:

Q. generally how much will be memory size of stack and heap, it depends on what explain in short?

Yes. **Stack and heap sizes are not fixed by JavaScript**; they depend mainly on the **JavaScript engine, runtime, platform, and configuration**.

### Typical idea

| Memory    | Typical size                      | Depends on                                                     |
| --------- | --------------------------------- | -------------------------------------------------------------- |
| **Stack** | Usually **a few MB**              | JS engine, runtime, thread/platform                            |
| **Heap**  | Usually **hundreds of MB to GBs** | Runtime, available system memory, engine limits, configuration |

For example, in **Node.js/V8**, the JavaScript heap has configurable limits and can grow substantially, while the call stack has a much smaller limit.

### Important interview point ⭐

Don't say:

> "Stack is always X MB and heap is always X GB."

Instead:

> **Stack and heap sizes are runtime/engine dependent. Stack is relatively small and limited, while heap is much larger and can grow within runtime-imposed limits.**

Also, **stack ≠ all memory used by JavaScript**, and **heap ≠ unlimited memory**.
