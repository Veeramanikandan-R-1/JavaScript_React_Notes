# JavaScript Basics — Interview Notes

## 1. Variables

Variables store values in JavaScript.

There are 3 ways to declare variables:

```js
var name = "John";
let age = 30;
const country = "India";
```

### `var` vs `let` vs `const`

|               | `var`    | `let` | `const` |
| ------------- | -------- | ----- | ------- |
| Scope         | Function | Block | Block   |
| Redeclaration | ✅        | ❌     | ❌       |
| Reassignment  | ✅        | ✅     | ❌       |
| Hoisted       | Yes      | Yes*  | Yes*    |
| TDZ           | ❌        | ✅     | ✅       |

### `let` / `const` ⭐

Prefer them in modern JavaScript:

```js
let count = 10;
count = 20;

const name = "John";
// name = "Bob"; // ❌
```

**Important:** `const` prevents **reassignment**, not mutation of objects/arrays.

```js
const user = { name: "John" };

user.name = "Bob"; // ✅
```

# 2. Scope

**Scope determines where a variable can be accessed.**

### Global Scope

```js
const appName = "My App";

function test() {
  console.log(appName); // ✅
}
```

### Function Scope

`var` is function-scoped:

```js
function test() {
  var x = 10;
}

console.log(x); // ❌
```

### Block Scope ⭐

`let` and `const` are block-scoped.

```js
if (true) {
  let x = 10;
  const y = 20;
}

console.log(x); // ❌
console.log(y); // ❌
```

A block is typically:

```js
{
  // block
}

if (...) {
  // block
}

for (...) {
  // block
}
```

### Lexical Scope

Inner functions can access variables from their outer scope:

```js
function outer() {
  const name = "John";

  function inner() {
    console.log(name); // ✅
  }

  inner();
}
```

This concept is important for understanding **closures**.

# 3. Hoisting ⭐⭐⭐

**Hoisting** is the behavior where JavaScript processes declarations before executing code in their scope.

### `var`

The declaration is hoisted and initialized with `undefined`.

```js
console.log(x); // undefined

var x = 10;
```

Conceptually:

```js
var x;
console.log(x);

x = 10;
```

---

### `let` and `const`

They are also hoisted, **but are not initialized** until execution reaches their declaration.

They are in the **Temporal Dead Zone (TDZ)** from the start of their scope until declaration.

```js
console.log(x); // ❌ ReferenceError

let x = 10;
```

```js
console.log(y); // ❌ ReferenceError

const y = 20;
```

### Function declaration

Function declarations are hoisted with their function body:

```js
sayHello(); // ✅

function sayHello() {
  console.log("Hello");
}
```

### Function expression

```js
sayHello(); // ❌ TypeError with var

var sayHello = function () {
  console.log("Hello");
};
```

Why?

```text
var sayHello → undefined
```

Calling `undefined()` causes `TypeError`.

### ⭐ Interview summary

```text
var           → hoisted + initialized as undefined
let/const     → hoisted + TDZ
function      → function declaration fully hoisted
```

# 4. Strict Mode

Strict mode makes JavaScript **stricter and safer** by changing/removing some error-prone behaviors.

Enable it with:

```js
"use strict";
```

### Example

Without strict mode:

```js
x = 10; // creates a global variable in sloppy mode
```

With strict mode:

```js
"use strict";

x = 10; // ❌ ReferenceError
```

### Other important effects

Strict mode:

* Prevents accidental global variables
* Throws errors for certain invalid assignments
* Makes some silent failures become errors
* Disallows some problematic legacy syntax
* Changes some `this` behavior

Example:

```js
"use strict";

function test() {
  console.log(this);
}

test(); // undefined
```

In non-strict mode, a plain function call can have `this` as the global object (in browsers, typically `window`).

### Important React point ⭐

Modern JavaScript modules are **implicitly strict mode**, and React applications using ES modules therefore generally run in strict mode without needing:

```js
"use strict";
```

Don't confuse JavaScript strict mode with React's:

```jsx
<React.StrictMode>
  <App />
</React.StrictMode>
```

`React.StrictMode` is a **React development feature**, not the same thing as JavaScript `"use strict"`.

Q. is js object oriented program?

Yes, **JavaScript is an object-oriented programming (OOP) language**, but more precisely, it is a **multi-paradigm language**.

### JavaScript supports OOP through:

* **Objects** – store data and behavior
* **Classes** – blueprint for creating objects
* **Encapsulation** – bundling data and methods
* **Inheritance** – one class can extend another
* **Polymorphism** – same method/interface can behave differently
* **Abstraction** – exposing only necessary details
* **Prototype-based inheritance** – JavaScript's underlying inheritance mechanism

Example:

```js
class Animal {
  constructor(name) {
    this.name = name;
  }

  speak() {
    console.log(`${this.name} makes a sound`);
  }
}

class Dog extends Animal {
  speak() {
    console.log(`${this.name} barks`);
  }
}

const dog = new Dog("Tommy");
dog.speak(); // Tommy barks
```

**Interview answer:**

> "JavaScript is a multi-paradigm language that supports object-oriented programming. Its OOP model is fundamentally prototype-based, while `class` syntax provides a more familiar way to implement OOP."

**Multi-paradigm** means JavaScript supports **multiple ways/styles of writing programs**, instead of forcing you to follow only one programming approach.

JavaScript mainly supports:

1. **Object-Oriented Programming (OOP)**

```js
class User {
  login() {
    console.log("Logged in");
  }
}
```

2. **Functional Programming**

```js
const numbers = [1, 2, 3];

const doubled = numbers.map(n => n * 2);
```

3. **Procedural Programming**

```js
function calculate(a, b) {
  const sum = a + b;
  return sum;
}

console.log(calculate(10, 20));
```

### Simple interview definition

> **JavaScript is a multi-paradigm language because it supports multiple programming paradigms such as object-oriented, functional, and procedural programming.**

Think of **paradigm = style/approach of programming**.

---

but in js class are just sytatic sugar right how then we can say ti is as object based?

Exactly 👍 — **JavaScript's `class` is largely syntactic sugar over its prototype-based inheritance system.** So the important distinction is:

> JavaScript is **object-oriented**, but its OOP model is **prototype-based**, not class-based like Java/C++.

### What actually happens?

When you write:

```js
class Animal {
  speak() {
    console.log("sound");
  }
}

const dog = new Animal();
```

The `speak()` method is actually placed on:

```js
Animal.prototype
```

So:

```js
dog.speak()
```

works roughly through the prototype chain:

```text
dog
 ↓
Animal.prototype
 ↓
Object.prototype
 ↓
null
```

### You can do OOP without `class`

This is completely valid JavaScript:

```js
const animal = {
  speak() {
    console.log("sound");
  }
};

const dog = Object.create(animal);

dog.speak();
```

Here there is **no class**, but we still have:

* Objects
* Encapsulation
* Inheritance through prototypes
* Polymorphic behavior

### So why call JavaScript object-oriented?

Because **OOP doesn't require classes**.

There are two common models:

```text
Class-based OOP
Java → Class → Object

Prototype-based OOP
JavaScript → Object → Object
```

JavaScript's **fundamental object model is prototype-based**. `class` was added mainly to provide cleaner, familiar syntax for constructing objects and working with prototypes.

### 🎯 Interview answer

> **"JavaScript is a multi-paradigm language and supports object-oriented programming. However, unlike Java, JavaScript is fundamentally prototype-based rather than class-based. The `class` syntax introduced in ES6 is syntactic sugar over JavaScript's existing prototype mechanism."**

That's the technically precise way to explain it.

Q. How JS engine works?

Sure. For interview purposes, understand a JavaScript engine like **V8** as this pipeline:

```text
JavaScript Code
      ↓
   Parser
      ↓
     AST
      ↓
Ignition (Bytecode)
      ↓
   Execute
      ↓
TurboFan (Optimization)
      ↓
Optimized Machine Code
```

### 1. Parser

You write:

```js
const x = 10;

function add(a, b) {
  return a + b;
}

console.log(add(x, 20));
```

The engine first **parses** the source code and creates an **AST (Abstract Syntax Tree)**.

```text
const x = 10
      ↓
VariableDeclaration
      ↓
x = 10
```

It also performs syntax/semantic checks.

---

### 2. Ignition — Bytecode

In V8, the AST is converted into **bytecode** by the **Ignition interpreter**.

```text
JavaScript
    ↓
Parser
    ↓
AST
    ↓
Ignition
    ↓
Bytecode
```

The bytecode is then executed.

---

### 3. JIT Optimization

If some code runs repeatedly, the engine identifies it as **hot code**.

Example:

```js
function add(a, b) {
  return a + b;
}

for (let i = 0; i < 1000000; i++) {
  add(i, 10);
}
```

`add()` gets called many times, so V8 may optimize it using **TurboFan**.

```text
Bytecode
   ↓
Hot code detected
   ↓
TurboFan
   ↓
Optimized Machine Code
```

This is **JIT (Just-In-Time) compilation**.

---

### 4. Deoptimization

Here's an important interview concept.

Suppose the engine assumes:

```js
function add(a, b) {
  return a + b;
}
```

is always receiving numbers.

Then you suddenly do:

```js
add(10, 20);       // numbers
add("Hello", "Hi"); // strings
```

The previous optimization may no longer be valid.

The engine can **deoptimize** and fall back to a less optimized execution path.

---

### 5. Memory management

The JS engine manages memory automatically.

```text
Memory
 ├── Stack
 │    └── Function calls / execution contexts
 │
 └── Heap
      └── Objects, arrays, functions, etc.
```

Example:

```js
const user = {
  name: "John"
};
```

The object is stored in the **heap**, while the variable/reference is managed through the execution environment.

The **Garbage Collector** removes objects that are no longer reachable.

---

### 6. Call Stack

When functions execute:

```js
function one() {
  two();
}

function two() {
  console.log("Hello");
}

one();
```

The call stack looks like:

```text
┌──────────────┐
│ console.log  │
├──────────────┤
│ two()        │
├──────────────┤
│ one()        │
└──────────────┘
```

Functions are pushed onto the stack when called and popped when finished.

---

### One important distinction

Don't mix up **JavaScript engine** and **browser**.

```text
             Browser
                │
       ┌────────┴────────┐
       │                 │
 JS Engine            Web APIs
   (V8)             DOM, Timer,
       │             Fetch, etc.
       │
 Parse/Compile/
 Execute JS
```

For example:

```js
setTimeout(() => {
  console.log("Hi");
}, 1000);
```

`setTimeout` isn't implemented purely by the JavaScript language itself. The **browser provides the timer Web API**; the JS engine executes the callback when it is eventually scheduled back onto the JS execution path.

### 🎯 Best interview summary

> **"A JavaScript engine such as V8 parses JavaScript into an AST, generates bytecode using the Ignition interpreter, executes it, and uses JIT compilation through TurboFan to optimize frequently executed code into machine code. It also manages memory using the heap, call stack, and garbage collector. Browser APIs such as DOM, timers, and fetch are provided by the browser environment, not by the JS engine itself."**

### ⭐ Must-know interview questions

**Q: Is `let`/`const` hoisted?**

> Yes, but they remain uninitialized in the **Temporal Dead Zone** until their declaration is evaluated.

**Q: `var` vs `let`?**

> `var` is function-scoped and can be redeclared; `let` is block-scoped and cannot be redeclared in the same scope.

**Q: Can a `const` object be modified?**

> Yes. `const` prevents reassignment of the variable binding, not mutation of the referenced object.
