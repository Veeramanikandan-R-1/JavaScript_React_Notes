# React Architecture 

> Interviewers expect you to know **how to organize a large React application**, not just how to create components. They may ask why you chose a particular folder structure, how you share logic, and how you keep the application scalable.

---

# 1. Folder Structure

A good folder structure should be:

* Easy to scale
* Easy to locate files
* Reduce coupling
* Increase reusability

## ❌ Small Project (Not Recommended for Enterprise)

```
src/
   components/
   pages/
   hooks/
   utils/
   services/
   App.jsx
```

Works for small applications but becomes messy as the project grows.

---

## ✅ Feature-Based Structure (Recommended)

```
src/
   features/
      users/
         components/
         hooks/
         services/
         api/
         utils/
         types/
         UserList.jsx
         UserDetails.jsx

      dashboard/
         components/
         hooks/
         services/

   shared/
      components/
      hooks/
      utils/
      constants/

   layouts/

   routes/

   store/

   assets/

   App.jsx
```

### Why?

Everything related to one feature stays together.

Instead of searching everywhere,

```
users component
users api
users hook
users styles
```

are all inside one folder.

Much easier to maintain.

---

## Enterprise Example

```
features/

   products/

      api/
         productApi.js

      hooks/
         useProducts.js

      components/
         ProductCard.jsx
         ProductList.jsx

      utils/
         formatPrice.js

      pages/
         ProductPage.jsx
```

---

# 2. Feature-Based Architecture

Instead of organizing by file type,

❌

```
components/
hooks/
services/
reducers/
```

Organize by business feature.

✅

```
Orders/
Users/
Products/
Dashboard/
```

Each feature owns:

* Components
* API
* Hooks
* Tests
* Styles
* Utilities

### Advantages

* Independent modules
* Easy code ownership
* Easier onboarding
* Better scalability
* Less merge conflicts

---

# 3. Component Composition

Instead of building one huge component,

compose small reusable components.

### ❌ Bad

```
Dashboard
    1200 lines
```

Contains:

* Sidebar
* Header
* Cards
* Table
* Charts
* Filters

Everything together.

---

### ✅ Better

```
Dashboard

    Header

    Filter

    CardList

        Card

    Table

    Footer
```

Each component has one responsibility.

---

### Example

```jsx
function Dashboard() {
  return (
    <>
      <Header />
      <Filters />
      <UserTable />
      <Pagination />
    </>
  );
}
```

Composition makes components:

* reusable
* testable
* readable

---

## Composition over Inheritance

React prefers

```
children
props
composition
```

instead of inheritance.

Example

```jsx
<Card>
    <UserProfile />
</Card>
```

instead of extending classes.

# 4. Smart vs Dumb Components

Also called

* Container vs Presentational

---

## Smart Component

Responsible for:

* API calls
* Redux
* Business logic
* State
* Event handling

Example

```jsx
function UserContainer() {
  const users = useUsers();

  return <UserList users={users} />;
}
```

---

## Dumb Component

Responsible only for UI.

Example

```jsx
function UserList({ users }) {
  return (
    <>
      {users.map(user => (
        <p key={user.id}>{user.name}</p>
      ))}
    </>
  );
}
```

No API

No Redux

No business logic

Only rendering.

---

## Advantages

Smart component

* manages logic

Dumb component

* reusable
* easy to test
* easy to reuse elsewhere

---

# 5. Container / Presentational Pattern

Very popular before Hooks.

Container

```
Fetch data

↓

Process data

↓

Pass props

↓

Presentational Component
```

Example

```jsx
function UserContainer() {
  const { data } = useUsers();

  return <UserTable users={data} />;
}
```

Presentational

```jsx
function UserTable({ users }) {
  return users.map(user => (
    <div key={user.id}>{user.name}</div>
  ));
}
```

---

## With Hooks

Nowadays,

Container logic is usually moved into Custom Hooks.

Example

```
Page

↓

useUsers()

↓

Component
```

Cleaner than old container components.

---

# 6. Custom Hooks Architecture

Custom hooks help separate business logic from UI.

---

Instead of

```jsx
function Dashboard() {

   useEffect(...)

   fetch(...)

   loading

   error

   retry

   pagination

   sorting

}
```

Move logic into hook.

---

Example

```jsx
function useUsers() {
  const [users, setUsers] = useState([]);

  useEffect(() => {
    fetchUsers().then(setUsers);
  }, []);

  return users;
}
```

Usage

```jsx
function Users() {
  const users = useUsers();

  return <UserList users={users} />;
}
```

---

## Folder Structure

```
hooks/

   useUsers.js

   usePagination.js

   useDebounce.js

   useAuth.js
```

---

## What should Custom Hook contain?

✔ Business logic

✔ API

✔ State

✔ Reusable logic

Should NOT return JSX.

---

## Good Naming

```
useUsers()

useProducts()

useTheme()

useDarkMode()

useInfiniteScroll()
```

Always starts with **use**.

---

```

```

Three almost identical buttons.

---

## ✅ Better

```jsx

    variant="primary"
    size="large"
>
    Save

```

---

### Another Example

Instead of

```
AdminTable

UserTable

OrderTable
```

Create

```jsx

    columns={}
    data={}
/>
```

---

## Characteristics

* Configurable through props
* No business-specific logic
* Small API
* Reusable
* Easy to test

# Common Architecture Flow (Enterprise)

```
UI Component

      ↓

Custom Hook

      ↓

API Service

      ↓

Axios

      ↓

Backend
```

Example

```
UserPage

↓

useUsers()

↓

userService.js

↓

axios.js

↓

REST API
```

This keeps UI completely separated from networking logic.

# Best Practices

* Prefer **feature-based architecture** for medium/large apps.
* Keep components **small** and focused on a single responsibility.
* Use **composition over inheritance**.
* Keep **business logic inside custom hooks** or state management, not UI components.
* Create **generic reusable components** (`Button`, `Input`, `Modal`, `Table`) instead of feature-specific ones.
* Keep API logic in **service files**, not directly inside components.
* Share common utilities and components through a `shared/` folder.

---

# Common Mistakes

❌ Putting all components inside one `components/` folder.

❌ Creating components with 500–1000 lines of code.

❌ Fetching APIs directly inside every component.

❌ Duplicating the same logic across multiple pages instead of using custom hooks.

❌ Creating reusable components that contain feature-specific business logic.

❌ Making every component stateful even when they only render UI.

| Topic                 | Remember                                                      |
| --------------------- | ------------------------------------------------------------- |
| Folder Structure      | Prefer feature-based over type-based for large apps           |
| Feature Architecture  | Keep components, hooks, services, utils together per feature  |
| Component Composition | Build UI by combining small components                        |
| Smart Component       | Handles state, API, business logic                            |
| Dumb Component        | Pure UI, receives props, reusable                             |
| Container Pattern     | Logic + data fetching; now often replaced by custom hooks     |
| Custom Hooks          | Reuse stateful/business logic, return data/functions, not JSX |
| Reusable Components   | Generic, configurable via props, no business logic            |
| Shared Folder         | Place common UI components, hooks, utils, constants           |

# Common 6-Year React Interview Questions

### 1. Which folder structure do you prefer in enterprise applications?

**Answer:** Feature-based architecture because it groups all related code (components, hooks, services, tests, styles) by business feature, making the application easier to scale and maintain.

---

### 2. Why is feature-based architecture better than type-based architecture?

**Answer:** It improves modularity, reduces coupling, simplifies navigation, enables better code ownership, and minimizes merge conflicts in large teams.

---

### 3. What is component composition?

**Answer:** Building complex UIs by combining small, reusable components instead of creating one large component. React encourages composition over inheritance.

---

### 4. What is the difference between Smart and Dumb components?

| Smart                   | Dumb                       |
| ----------------------- | -------------------------- |
| Contains business logic | Only renders UI            |
| Manages state           | Receives props             |
| API calls               | No API calls               |
| Uses Redux/hooks        | Stateless or minimal state |
| Less reusable           | Highly reusable            |

---

### 5. Is the Container/Presentational pattern still used?

**Answer:** The concept is still relevant, but in modern React the container logic is commonly extracted into custom hooks instead of separate container components.

---

### 6. What should a custom hook return?

**Answer:** State values, functions, and reusable logic. A custom hook should never return JSX.

---

### 7. What makes a component reusable?

**Answer:** It is generic, configurable through props, independent of business logic, easy to test, and usable across multiple features.

---

### 8. Where should API calls be placed?

**Answer:** Ideally in service modules, with business logic managed by custom hooks. Components should focus on rendering UI.

---

### 9. How do you avoid large React components?

**Answer:** Break them into smaller components, move reusable logic to custom hooks, extract API calls into services, and compose the UI from focused pieces.

---

### 10. How would you structure a large React application?

**Expected answer:**

```
src/
 ├── features/
 ├── shared/
 ├── layouts/
 ├── routes/
 ├── services/
 ├── store/
 ├── assets/
 └── App.jsx
```

Each feature contains its own components, hooks, services, tests, and utilities, while shared resources live under `shared/`. This structure keeps the codebase modular and scalable.
