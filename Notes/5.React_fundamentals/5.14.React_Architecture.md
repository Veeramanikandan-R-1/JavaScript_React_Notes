# React JS — React Architecture

> For a 5-year React developer, the key is not just knowing patterns, but knowing **when and why to use them**. Modern React generally favors **feature-based organization + composition + custom hooks**, rather than rigid component patterns.

---

# 1. Folder Structure

A good structure should make code **easy to find, maintain, test, and scale**.

### Small/medium application

```text
src/
├── components/
│   ├── Button/
│   ├── Modal/
│   └── Input/
│
├── pages/
│   ├── Home/
│   └── Users/
│
├── hooks/
├── services/
├── utils/
├── store/
├── routes/
├── assets/
├── App.jsx
└── main.jsx
```

### Larger application → Feature-based

```text
src/
├── features/
│   ├── auth/
│   │   ├── components/
│   │   ├── hooks/
│   │   ├── authSlice.js
│   │   ├── authApi.js
│   │   └── utils.js
│   │
│   ├── users/
│   │   ├── components/
│   │   ├── hooks/
│   │   ├── userApi.js
│   │   └── userSlice.js
│   │
│   └── dashboard/
│       ├── components/
│       └── hooks/
│
├── components/       # Shared UI
├── hooks/            # Shared hooks
├── services/         # Shared API/infrastructure
├── utils/
├── routes/
└── App.jsx
```

### Interview point

> Folder structure should follow **project complexity and team needs**, not a fixed universal rule.

# 2. Feature-Based Architecture

Organize code around **business features**, rather than technical types.

### ❌ Type-based

```text
components/
hooks/
services/
reducers/
```

Everything related to users may be spread across multiple folders.

### ✅ Feature-based

```text
features/
└── users/
    ├── components/
    ├── hooks/
    ├── userApi.js
    ├── userSlice.js
    └── userUtils.js
```

All user-related functionality stays together.

### Benefits

* Better scalability
* Easier maintenance
* Clear ownership
* Reduced coupling
* Easier onboarding
* Feature can be developed/tested independently

### Example

```jsx
// features/users/components/UserList.jsx

function UserList({ users }) {
  return (
    <ul>
      {users.map(user => (
        <li key={user.id}>{user.name}</li>
      ))}
    </ul>
  );
}
```

# 3. Component Composition

**Composition = building complex UI by combining smaller components.**

Instead of creating one huge component, compose smaller components.

```jsx
function Card({ header, children, footer }) {
  return (
    <div className="card">
      <header>{header}</header>

      <main>{children}</main>

      <footer>{footer}</footer>
    </div>
  );
}
```

Usage:

```jsx
<Card
  header={<h2>User</h2>}
  footer={<button>Save</button>}
>
  <UserForm />
</Card>
```

### `children`

React's primary composition mechanism:

```jsx
function Modal({ children }) {
  return (
    <div className="modal">
      {children}
    </div>
  );
}
```

### Why composition?

Prefer:

```text
Small components
      ↓
Composition
      ↓
Reusable UI
```

instead of deep inheritance hierarchies.

> **React favors composition over inheritance.**

# 4. Smart vs Dumb Components

Older/common terminology:

### Smart Component

Responsible for:

* Data fetching
* State
* Business logic
* Dispatching actions
* Passing data to UI

```jsx
function UserContainer() {
  const [users, setUsers] = useState([]);

  useEffect(() => {
    fetchUsers().then(setUsers);
  }, []);

  return <UserList users={users} />;
}
```

### Dumb Component

Primarily responsible for presentation.

```jsx
function UserList({ users }) {
  return (
    <ul>
      {users.map(user => (
        <li key={user.id}>{user.name}</li>
      ))}
    </ul>
  );
}
```

### Important

This distinction is a **design guideline**, not a strict React rule.

Modern React often moves logic into **custom hooks**, making components cleaner.

# 5. Container / Presentational Pattern

This is closely related to Smart/Dumb components.

### Container

Handles:

```text
Data
State
Business logic
API
```

### Presentational

Handles:

```text
UI
Props
User interactions
```

Example:

```jsx
function UserContainer() {
  const [users, setUsers] = useState([]);

  useEffect(() => {
    getUsers().then(setUsers);
  }, []);

  return (
    <UserList
      users={users}
      onDelete={(id) => {
        // logic
      }}
    />
  );
}
```

Presentational:

```jsx
function UserList({ users, onDelete }) {
  return (
    <>
      {users.map(user => (
        <div key={user.id}>
          {user.name}

          <button onClick={() => onDelete(user.id)}>
            Delete
          </button>
        </div>
      ))}
    </>
  );
}
```

### Modern approach

Instead of:

```text
Container Component
       ↓
Presentational Component
```

often use:

```text
Component
    ↓
Custom Hook → business/data logic
    ↓
Component → UI
```

# 6. Custom Hooks Architecture

Custom hooks are excellent for **reusing stateful logic**, not UI.

### Example

```jsx
function useUsers() {
  const [users, setUsers] = useState([]);
  const [loading, setLoading] = useState(false);

  const fetchUsers = async () => {
    setLoading(true);

    try {
      const response = await api.get("/users");
      setUsers(response.data);
    } finally {
      setLoading(false);
    }
  };

  useEffect(() => {
    fetchUsers();
  }, []);

  return {
    users,
    loading,
    refetch: fetchUsers,
  };
}
```

Component:

```jsx
function UsersPage() {
  const { users, loading, refetch } = useUsers();

  if (loading) {
    return <Spinner />;
  }

  return (
    <>
      <UserList users={users} />
      <button onClick={refetch}>Refresh</button>
    </>
  );
}
```

### Architecture

```text
UsersPage
    │
    ├── useUsers()
    │      ├── API
    │      ├── state
    │      └── business logic
    │
    └── UserList
           └── UI
```

### Good custom hook characteristics

* Starts with `use`
* Encapsulates reusable behavior
* Has a focused responsibility
* Returns a clean API
* Doesn't unnecessarily contain UI

# 7. Reusable Components

A reusable component should be:

* Generic enough to reuse
* Configurable through props
* Composable
* Accessible
* Predictable
* Independent of business-specific logic

### Example

```jsx
function Button({
  children,
  variant = "primary",
  disabled = false,
  onClick,
}) {
  return (
    <button
      className={`btn btn-${variant}`}
      disabled={disabled}
      onClick={onClick}
    >
      {children}
    </button>
  );
}
```

Usage:

```jsx
<Button onClick={saveUser}>
  Save
</Button>

<Button variant="danger" onClick={deleteUser}>
  Delete
</Button>
```

### Avoid over-generalization

Don't create:

```jsx
<UniversalComponent
  type="button"
  mode="x"
  variant="y"
  renderSomething={...}
  config={...}
/>
```

if the abstraction becomes harder to understand than separate components.

> **Rule:** Abstract when you have a real reuse pattern, not just because two components look slightly similar.

---

# 8. Component API Design

For reusable components, design a clean **public API**.

### Good

```jsx
<Modal
  open={isOpen}
  onClose={handleClose}
  title="Delete User"
>
  <DeleteConfirmation />
</Modal>
```

### Avoid exposing internal implementation

```jsx
<Modal
  setInternalState={...}
  internalMode={...}
  internalConfig={...}
/>
```

Consumers should interact through meaningful props.

# 9. Recommended Architecture

For a large React application:

```text
                    App
                     │
                 Routing
                     │
             ┌───────┴───────┐
             │               │
         Feature A       Feature B
             │               │
       ┌─────┴─────┐   ┌─────┴─────┐
       │           │   │           │
   Components   Hooks Components  Hooks
       │           │       │         │
       │        Services   │      Services
       │           │       │         │
       └───────────┴───────┴─────────┘
                     │
              Shared Components
```

### Practical separation

```text
UI
 ↓
Components

Stateful / Business Logic
 ↓
Custom Hooks

Server Communication
 ↓
API Services / RTK Query

Global Client State
 ↓
Redux / Zustand

Pure Helpers
 ↓
Utils
```

# ⭐ Interview Cheat Sheet

| Concept            | Purpose                                  |
| ------------------ | ---------------------------------------- |
| Folder structure   | Organize code for maintainability        |
| Feature-based      | Group code by business feature           |
| Composition        | Build complex UI from smaller components |
| Smart component    | Handles state/data/business logic        |
| Dumb component     | Primarily renders UI from props          |
| Container          | Data/state/business logic                |
| Presentational     | UI/presentation                          |
| Custom Hook        | Reuse stateful/business logic            |
| Reusable component | Reuse UI through a clean prop API        |

### ⭐ Key interview answers

**Q: Feature-based vs component-based folder structure?**

> Feature-based architecture groups related code by business domain, which scales better for large applications because changes to a feature remain localized.

**Q: Smart vs Dumb components?**

> Smart components handle data/state/business logic, while dumb components focus mainly on presentation. It's a useful guideline rather than a strict rule in modern React.

**Q: Custom hook vs reusable component?**

> A custom hook reuses **logic/behavior**; a reusable component reuses **UI/structure**.

**Q: Composition vs inheritance?**

> React favors **composition**. Instead of extending components through inheritance, compose smaller components using `children`, props, and render patterns.

**Q: What architecture would you choose for a large React application?**

> I'd typically use **feature-based architecture**, keep reusable UI in shared components, extract reusable business/stateful logic into custom hooks, isolate API communication, and use an appropriate state-management solution for genuinely global state.
