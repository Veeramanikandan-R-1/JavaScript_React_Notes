# React JS — Redux Saga

> **Redux Saga** is a Redux middleware used to handle **side effects** such as API calls, async workflows, polling, debouncing, retries, and complex business processes.

For a 5-year React developer, focus especially on **Generators, `call`, `put`, `takeLatest`, `takeEvery`, cancellation, and Saga flow**.

---

# 1. Why Redux Saga?

Without Saga:

```text
Component
   ↓
dispatch(action)
   ↓
Reducer
```

For async operations, Saga sits between dispatch and reducers:

```text
Component
   ↓
dispatch(FETCH_USERS)
   ↓
Redux Saga
   ↓
API call
   ↓
dispatch(FETCH_USERS_SUCCESS)
   ↓
Reducer
   ↓
Store
```

### Why use it?

Useful for complex async workflows:

* API calls
* Multiple dependent API calls
* Retry logic
* Polling
* Debouncing
* Cancellation
* Race conditions
* Background tasks
* Complex orchestration

---

# 2. Generator Functions

Redux Saga is built heavily around **JavaScript Generator functions**.

Syntax:

```js
function* mySaga() {
  yield something();
}
```

`function*` creates a generator.

`yield` pauses execution and allows Saga middleware to control the workflow.

Example:

```js
function* testSaga() {
  console.log("Start");

  yield delay(1000);

  console.log("After 1 second");
}
```

Think:

```text
yield
 ↓
Pause / delegate control to Saga middleware
 ↓
Effect completes
 ↓
Continue
```

---

# 3. Effects

Saga uses **effects** to describe what should happen.

Common effects:

| Effect       | Purpose                 |
| ------------ | ----------------------- |
| `call`       | Call a function/API     |
| `put`        | Dispatch Redux action   |
| `take`       | Wait for an action      |
| `takeEvery`  | Handle every occurrence |
| `takeLatest` | Handle only latest      |
| `select`     | Read Redux state        |
| `fork`       | Start non-blocking task |
| `cancel`     | Cancel task             |
| `race`       | Race multiple effects   |
| `delay`      | Wait for specified time |
| `all`        | Run multiple effects    |

---

# 4. `call`

Used to invoke a function, commonly an API.

```js
import { call } from "redux-saga/effects";

function* fetchUsersSaga() {
  const response = yield call(api.getUsers);

  console.log(response);
}
```

Instead of:

```js
const response = await api.getUsers();
```

Saga uses:

```js
yield call(api.getUsers);
```

### Why `call`?

It creates a declarative effect that Saga middleware executes.

It also makes generator-based workflows easier to test.

---

# 5. `put`

Used to dispatch a Redux action.

```js
import { put } from "redux-saga/effects";

yield put({
  type: "FETCH_USERS_SUCCESS",
  payload: users,
});
```

With action creators:

```js
yield put(fetchUsersSuccess(users));
```

Flow:

```text
API success
   ↓
put(successAction)
   ↓
Reducer
   ↓
Store updated
```

# 6. Basic API Saga

### Actions

```js
const FETCH_USERS = "FETCH_USERS";
const FETCH_USERS_SUCCESS = "FETCH_USERS_SUCCESS";
const FETCH_USERS_FAILURE = "FETCH_USERS_FAILURE";
```

### Worker Saga

```js
function* fetchUsersSaga() {
  try {
    const response = yield call(api.getUsers);

    yield put({
      type: FETCH_USERS_SUCCESS,
      payload: response.data,
    });
  } catch (error) {
    yield put({
      type: FETCH_USERS_FAILURE,
      payload: error.message,
    });
  }
}
```

---

# 7. `takeEvery`

Runs a new saga for **every dispatched action**.

```js
import { takeEvery } from "redux-saga/effects";

function* rootSaga() {
  yield takeEvery("FETCH_USERS", fetchUsersSaga);
}
```

If user dispatches:

```text
FETCH_USERS
FETCH_USERS
FETCH_USERS
```

all three can execute.

### Use cases

Good for independent operations:

* Logging
* Analytics
* Processing independent events

---

# 8. `takeLatest`

Cancels the previous running task when a new matching action arrives.

```js
function* rootSaga() {
  yield takeLatest("SEARCH_USERS", searchUsersSaga);
}
```

Example:

```text
User types:

R
Re
Rea
React
```

Instead of processing every request:

```text
R     → API
Re    → API
Rea   → API
React → API
```

`takeLatest` keeps the latest workflow:

```text
R
 ↓ cancel

Re
 ↓ cancel

Rea
 ↓ cancel

React
 ↓
API
```

### Very common use cases

* Search/autocomplete
* Filters
* Latest data fetch

---

# 9. `take` vs `takeEvery` vs `takeLatest`

### `take`

Wait for **one specific action**:

```js
const action = yield take("LOGIN");
```

### `takeEvery`

Handle **every action**:

```js
yield takeEvery("LOGIN", loginSaga);
```

### `takeLatest`

Handle **only latest**, cancel previous:

```js
yield takeLatest("SEARCH", searchSaga);
```

### Interview shortcut

```text
take        → wait
takeEvery   → all
takeLatest  → latest
```

# 10. `select`

Reads data from Redux store.

```js
import { select } from "redux-saga/effects";

const user = yield select(
  state => state.auth.user
);
```

Better with a selector:

```js
const user = yield select(selectCurrentUser);
```

Useful when API request depends on current Redux state.

---

# 11. Error Handling

Use normal `try/catch`.

```js
function* fetchUsersSaga() {
  try {
    const response = yield call(api.getUsers);

    yield put(fetchSuccess(response.data));
  } catch (error) {
    yield put(fetchFailure(error.message));
  }
}
```

Flow:

```text
API
 ├── Success → SUCCESS action
 │
 └── Error   → FAILURE action
```

---

# 12. `fork`

Starts a task **without blocking** the current saga.

```js
import { fork } from "redux-saga/effects";

function* rootSaga() {
  yield fork(watchUsers);
  yield fork(watchAuth);
}
```

Conceptually:

```text
rootSaga
   │
   ├── fork → user watcher
   │
   └── fork → auth watcher

Both can run independently.
```

---

# 13. `all`

Runs multiple effects together.

```js
import { all, fork } from "redux-saga/effects";

export default function* rootSaga() {
  yield all([
    fork(watchUsers),
    fork(watchAuth),
    fork(watchProducts),
  ]);
}
```

Common root Saga pattern.

---

# 14. Saga Architecture

Typical structure:

```text
store/
├── actions/
├── reducers/
└── sagas/
    ├── userSaga.js
    ├── authSaga.js
    ├── productSaga.js
    └── index.js
```

### Root Saga

```js
import { all, fork } from "redux-saga/effects";

export default function* rootSaga() {
  yield all([
    fork(userSaga),
    fork(authSaga),
    fork(productSaga),
  ]);
}
```

# 15. Connecting Saga to Redux

```js
import createSagaMiddleware from "redux-saga";

const sagaMiddleware = createSagaMiddleware();

const store = createStore(
  rootReducer,
  applyMiddleware(sagaMiddleware)
);

sagaMiddleware.run(rootSaga);
```

With Redux Toolkit:

```js
const sagaMiddleware = createSagaMiddleware();

const store = configureStore({
  reducer: rootReducer,

  middleware: (getDefaultMiddleware) =>
    getDefaultMiddleware({
      thunk: false,
    }).concat(sagaMiddleware),
});

sagaMiddleware.run(rootSaga);
```

> If you're using Redux Toolkit, `redux-thunk` is enabled by default. Disable it only if your architecture intentionally uses Saga instead.

# 16. Cancellation

Saga supports cancellation of running tasks.

```js
import {
  fork,
  cancel,
  take,
} from "redux-saga/effects";

function* watcher() {
  const task = yield fork(longRunningTask);

  yield take("STOP_TASK");

  yield cancel(task);
}
```

`takeLatest` also uses Saga cancellation behavior internally.

---

# 17. `race`

Useful when multiple operations compete and you want the first one to finish.

Example: API request vs timeout.

```js
import { race, call, delay } from "redux-saga/effects";

function* fetchWithTimeout() {
  const { response, timeout } = yield race({
    response: call(api.getUsers),
    timeout: delay(5000),
  });

  if (timeout) {
    throw new Error("Request timed out");
  }

  return response;
}
```

Concept:

```text
             ┌── API ────────┐
race() ──────┤                ├── First result wins
             └── 5 sec timer ─┘
```

---

# 18. Retry

Saga provides a `retry` effect.

```js
import { retry } from "redux-saga/effects";

const response = yield retry(
  3,
  1000,
  api.getUsers
);
```

Meaning:

```text
Try
 ↓
Failure
 ↓
wait 1 sec
 ↓
Try again
 ↓
Failure
 ↓
Try again
```

For more sophisticated retry logic, you can implement exponential backoff manually.

---

# 19. Debouncing

Useful for search boxes.

```js
import { debounce } from "redux-saga/effects";

function* searchSaga(action) {
  yield call(api.search, action.payload);
}

function* rootSaga() {
  yield debounce(
    500,
    "SEARCH_USERS",
    searchSaga
  );
}
```

Meaning:

> Wait until the user stops dispatching `SEARCH_USERS` for 500ms, then execute the latest search.

# 20. Redux Saga vs Redux Thunk

| Redux Thunk                  | Redux Saga                       |
| ---------------------------- | -------------------------------- |
| Simpler                      | More powerful                    |
| Async logic inside functions | Generator-based workflows        |
| Less boilerplate             | More concepts                    |
| Good for simple API calls    | Good for complex async workflows |
| `async/await`                | `function*` + effects            |
| Easier to learn              | Steeper learning curve           |

### Example

**Thunk:**

```js
const fetchUsers = () => async dispatch => {
  const response = await api.getUsers();

  dispatch(setUsers(response.data));
};
```

**Saga:**

```js
function* fetchUsersSaga() {
  const response = yield call(api.getUsers);

  yield put(setUsers(response.data));
}
```

Remember this for interviews:

```text

    │

    │
    ▼

    │
    ▼

    │
    ▼

```

# ⭐ Most Important Effects to Remember

```text
call()     → call API/function
put()      → dispatch action
select()   → read Redux state
take()     → wait for action
fork()     → start non-blocking task
cancel()   → cancel task
race()     → first effect wins
delay()    → wait
all()      → run effects together
```

### Watchers

```text
takeEvery()  → execute every time
takeLatest() → only latest, cancel previous
debounce()   → wait until events stop
throttle()   → limit execution frequency
```

### ⭐ Interview questions

**Q: Why use Redux Saga?**

> Redux Saga is useful when an application has complex asynchronous workflows such as dependent API calls, cancellation, polling, retries, debouncing, and background processes.

**Q: Why generators?**

> Generators allow Saga to pause and resume execution around yielded effects, giving the middleware control over asynchronous workflows.

**Q: `call` vs `put`?**

> `call` invokes a function/API through a Saga effect; `put` dispatches a Redux action.

**Q: `takeEvery` vs `takeLatest`?**

> `takeEvery` processes every matching action concurrently, while `takeLatest` cancels the previous running task and processes the latest one.

**Q: `fork` vs `call`?**

> `call` is blocking—the Saga waits for the function/effect to complete. `fork` starts a non-blocking task and immediately allows the parent Saga to continue.

**Q: Is Redux Saga still useful?**

> Yes, particularly for applications with complex async orchestration. For straightforward API fetching, Redux Toolkit's **RTK Query** is often a simpler modern choice; Saga becomes more valuable when the workflow itself is complex.
