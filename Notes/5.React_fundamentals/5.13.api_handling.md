# React JS — API Handling

> **Interview mindset:** Separate **API communication**, **authentication**, **authorization**, **error handling**, and **request lifecycle**. In real applications, centralize common API behavior instead of duplicating it in every component.

---

# 1. `fetch`

Built-in browser API for making HTTP requests.

### GET

```js
const response = await fetch("/api/users");

if (!response.ok) {
  throw new Error(`HTTP ${response.status}`);
}

const data = await response.json();
```

### POST

```js
const response = await fetch("/api/users", {
  method: "POST",
  headers: {
    "Content-Type": "application/json",
  },
  body: JSON.stringify({
    name: "John",
    email: "john@example.com",
  }),
});

const data = await response.json();
```

### Important

`fetch()` **doesn't reject the Promise for HTTP errors** like `400` or `500`.

```js
fetch("/api/users")
  .then(res => {
    if (!res.ok) throw new Error("Request failed");
    return res.json();
  });
```

It rejects mainly for **network-level failures, aborts, etc.**

# 2. Axios

Axios is a third-party HTTP client providing features such as:

* Request/response interceptors
* Automatic JSON transformation
* Timeout configuration
* Better request configuration
* Request cancellation
* Convenient error object
* Global defaults

### GET

```js
import axios from "axios";

const response = await axios.get("/api/users");

console.log(response.data);
```

### POST

```js
await axios.post("/api/users", {
  name: "John",
  email: "john@example.com",
});
```

### Axios Instance

Prefer creating a centralized instance:

```js
const api = axios.create({
  baseURL: "/api",
  timeout: 10000,
});

export default api;
```

Then:

```js
api.get("/users");
api.post("/users", user);
```

# 3. CRUD

CRUD = **Create, Read, Update, Delete**

| Operation | HTTP      | Example    |
| --------- | --------- | ---------- |
| Create    | POST      | `/users`   |
| Read      | GET       | `/users/1` |
| Update    | PUT/PATCH | `/users/1` |
| Delete    | DELETE    | `/users/1` |

### Example

```js
// Create
await api.post("/users", user);

// Read
await api.get("/users");

// Update
await api.patch("/users/1", { name: "Mike" });

// Delete
await api.delete("/users/1");
```

### PUT vs PATCH

**PUT**

* Usually replaces the complete resource.

**PATCH**

* Partially updates the resource.

# 4. Interceptors

Interceptors allow you to run logic **before requests** or **after responses**.

Common use cases:

* Add access token
* Add common headers
* Logging
* Centralized error handling
* Handle `401`
* Refresh expired token

### Request Interceptor

```js
api.interceptors.request.use((config) => {
  const token = localStorage.getItem("accessToken");

  if (token) {
    config.headers.Authorization = `Bearer ${token}`;
  }

  return config;
});
```

### Response Interceptor

```js
api.interceptors.response.use(
  (response) => response,

  (error) => {
    if (error.response?.status === 401) {
      // Handle authentication failure
    }

    return Promise.reject(error);
  }
);
```

### Interview point

> Interceptors are useful for cross-cutting HTTP concerns that should apply to multiple API requests.

# 5. Authentication vs Authorization

### Authentication

**"Who are you?"**

Verifies user identity.

```text
Login
 ↓
Credentials
 ↓
Server verifies
 ↓
Token/session
```

### Authorization

**"What are you allowed to do?"**

Determines permissions.

```text
User
 ↓
Role: ADMIN
 ↓
Can access /admin
```

Example:

```jsx
if (user.role === "ADMIN") {
  return <AdminDashboard />;
}
```

**Important:** Frontend authorization is only for UI/UX. The **backend must enforce authorization**.

# 6. JWT

**JWT = JSON Web Token**

Commonly used for stateless authentication.

Structure:

```text
Header.Payload.Signature
```

Example conceptually:

```text
xxxxx.yyyyy.zzzzz
```

Payload might contain:

```json
{
  "sub": "123",
  "role": "admin",
  "exp": 1788000000
}
```

### Typical flow

```text
React
  │
  │ POST /login
  ▼
Backend
  │
  │ access token
  ▼
React
  │
  │ Authorization: Bearer <token>
  ▼
Protected API
```

### Important JWT concepts

* `exp` → expiration
* `sub` → subject/user identifier
* Signature → verifies token integrity
* JWT is **signed, not encrypted by default**
* Don't put sensitive secrets in the payload.

# 7. Refresh Token

Access tokens should generally be **short-lived**.

When the access token expires:

```text
Access Token expired
       ↓
API → 401
       ↓
Refresh Token
       ↓
/refresh
       ↓
New Access Token
       ↓
Retry original request
```

### Example interceptor concept

```js
api.interceptors.response.use(
  response => response,

  async (error) => {
    const originalRequest = error.config;

    if (
      error.response?.status === 401 &&
      !originalRequest._retry
    ) {
      originalRequest._retry = true;

      const response = await api.post("/auth/refresh");

      const newToken = response.data.accessToken;

      localStorage.setItem("accessToken", newToken);

      originalRequest.headers.Authorization =
        `Bearer ${newToken}`;

      return api(originalRequest);
    }

    return Promise.reject(error);
  }
);
```

### Production concerns

A robust refresh implementation should also handle:

* Multiple simultaneous `401`s
* Refresh request itself failing
* Logout/session expiration
* Infinite retry loops
* Race conditions

### Security point

A common architecture is:

```text
Access Token → short-lived
Refresh Token → longer-lived
```

Refresh tokens are often stored in a **Secure, HttpOnly cookie**, reducing exposure to JavaScript-based token theft. Exact storage architecture depends on your backend/security requirements.

# 8. Error Handling

Handle different categories separately.

```js
try {
  const response = await api.get("/users");
  setUsers(response.data);
} catch (error) {
  if (error.response) {
    // Server responded with 4xx/5xx
    console.log(error.response.status);
  } else if (error.request) {
    // Request sent but no response
    console.log("Network/server unavailable");
  } else {
    // Request configuration/setup error
    console.log(error.message);
  }
}
```

### Common HTTP status codes

```text
200 → OK
201 → Created
204 → No Content

400 → Bad Request
401 → Unauthenticated
403 → Forbidden
404 → Not Found
409 → Conflict
422 → Validation error
429 → Too Many Requests

500 → Server error
502 → Bad Gateway
503 → Service Unavailable
```

### 401 vs 403

**401**

> User is not authenticated / token invalid or expired.

**403**

> User is authenticated but doesn't have permission.

# 9. Retry

Retry means automatically sending a failed request again.

Useful for **temporary failures**, such as:

* Network failure
* `408`
* `429`
* `502`
* `503`
* `504`

Don't blindly retry every error.

For example:

```text
400 → Don't retry
401 → Refresh token / authenticate
403 → Don't retry
404 → Usually don't retry
429 → Retry after delay
503 → Retry
```

### Exponential Backoff

Instead of:

```text
retry immediately
retry immediately
retry immediately
```

use:

```text
1st retry → 1 sec
2nd retry → 2 sec
3rd retry → 4 sec
```

Concept:

```js
const delay = 1000 * 2 ** attempt;

await new Promise(resolve =>
  setTimeout(resolve, delay)
);
```

Add **jitter** in production to prevent many clients from retrying simultaneously.

# 10. Cancellation

Useful when the request is no longer needed.

Typical React scenario:

```text
Component mounts
     ↓
API request
     ↓
Component unmounts
     ↓
Cancel request
```

## Fetch — `AbortController`

```js
useEffect(() => {
  const controller = new AbortController();

  fetch("/api/users", {
    signal: controller.signal,
  })
    .then(res => res.json())
    .then(data => setUsers(data))
    .catch(error => {
      if (error.name !== "AbortError") {
        console.error(error);
      }
    });

  return () => {
    controller.abort();
  };
}, []);
```

## Axios

Modern Axios also supports `AbortController`:

```js
const controller = new AbortController();

api.get("/users", {
  signal: controller.signal,
});

controller.abort();
```

### Why cancellation?

Prevents:

* Unnecessary network work
* Updating UI with stale results
* Race conditions
* Wasted resources

# ⭐ Complete API Architecture

For a real React application, aim for:

```text
                    React Component
                          │
                          ▼
                    API Service
                          │
                          ▼
                  Axios Instance
                          │
              ┌───────────┴───────────┐
              │                       │
       Request Interceptor      Response Interceptor
              │                       │
        Add Access Token         Handle 401
                                      │
                               Refresh Token
                                      │
                               Retry Request
                                      │
                                      ▼
                                   Backend
```

Example structure:

```text
src/
├── api/
│   ├── axios.js
│   ├── authApi.js
│   └── userApi.js
│
├── components/
├── hooks/
├── store/
└── utils/
```

### ⭐ Common interview questions

**Q: Why use Axios instead of fetch?**

> Axios provides conveniences such as interceptors, instances, timeout configuration, automatic JSON handling, and a more consistent error/request API. `fetch` is native and is perfectly suitable when those abstractions aren't needed.

**Q: Where should token logic go?**

> Usually in a centralized API client/interceptor rather than inside every component.

**Q: What happens when an access token expires?**

> The API commonly returns `401`; the client uses the refresh mechanism to obtain a new access token and retries the original request.

**Q: Should every failed request be retried?**

> No. Retry only appropriate transient failures, use bounded attempts and exponential backoff, and avoid retrying non-idempotent operations blindly.

**Q: 401 vs 403?**

> **401 = authentication problem. 403 = permission problem.**

**Q: Why cancel API requests in React?**

> To prevent unnecessary work and stale/race-condition updates when a component unmounts or a newer request supersedes an older one.
