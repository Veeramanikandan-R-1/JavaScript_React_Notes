# Authentication — Interview Notes

Since this is **not your main focus**, I’d prepare this at a **conceptual + practical React level**. At 6 years of experience, the interviewer will likely care more about whether you understand **how authentication works, where tokens are stored, and common security risks** than cryptographic details.

---

## 1. JWT

**JWT = JSON Web Token**

JWT is a token format commonly used to represent authenticated user information/claims.

Typical flow:

```text
User
  ↓
Login (username/password)
  ↓
Backend
  ↓
JWT
  ↓
Frontend
  ↓
API requests
  ↓
Backend validates JWT
```

A JWT looks roughly like:

```text
xxxxx.yyyyy.zzzzz
```

It has 3 parts:

```text
Header.Payload.Signature
```

### Payload

Contains claims such as:

```json
{
  "sub": "123",
  "role": "admin",
  "exp": 1234567890
}
```

**Important:** JWT payload is typically **encoded, not encrypted**.

So don't put sensitive information like passwords or secrets inside it.

### Access token vs Refresh token

Common architecture:

```text
Access Token
→ Short-lived
→ Used to access APIs

Refresh Token
→ Longer-lived
→ Used to obtain a new access token
```

Example:

```text
Access Token → 15 min
Refresh Token → days/weeks
```

Exact lifetimes depend on the application.

### Interview question

**Q: Is JWT authentication or authorization?**

JWT itself is a **token format**. It can carry authentication-related information and authorization claims.

A useful answer:

> "JWT is a token format. After authentication, the server can issue a JWT containing claims, and APIs can use those claims to authorize requests."

# 2. OAuth Basics

**OAuth 2.0 is primarily an authorization framework**, not simply a login protocol.

It allows an application to obtain limited access to resources on behalf of a user without receiving the user's password.

Example:

```text
Your App
   ↓
"Sign in with Google"
   ↓
Google authorization server
   ↓
User grants permission
   ↓
Authorization code
   ↓
Your backend/app
   ↓
Tokens
```

### Important terminology

You should recognize:

```text
Resource Owner → User

Client → Your application

Authorization Server → Issues tokens

Resource Server → API/resource being accessed
```

### Authorization Code Flow

For modern web applications, the **Authorization Code flow with PKCE** is an important concept.

High level:

```text
User
 ↓
Your App
 ↓
Authorization Server
 ↓
User authenticates
 ↓
Authorization Code
 ↓
Your App exchanges code
 ↓
Access Token
```

### OAuth vs JWT

Don't confuse them.

> **OAuth = authorization framework/protocol.**
> **JWT = token format.**

OAuth tokens don't necessarily have to be JWTs.

# 3. Session

A **session-based authentication** system stores authentication state on the server.

Typical flow:

```text
Login
  ↓
Server validates credentials
  ↓
Server creates session
  ↓
Session ID sent to browser
  ↓
Browser sends session ID with requests
  ↓
Server finds session
  ↓
User authenticated
```

Example:

```text
Browser
   |
   | Cookie: sessionId=abc123
   ↓
Server
   |
   ↓
Session Store
   |
   ↓
User information
```

### Session vs JWT

| Session                          | JWT                                         |
| -------------------------------- | ------------------------------------------- |
| State stored server-side         | Claims carried in token                     |
| Client usually stores session ID | Client sends token                          |
| Easy server-side invalidation    | Stateless access-token validation is common |
| Requires session storage         | Doesn't necessarily require session storage |
| Often uses cookies               | Can use cookies or other mechanisms         |

### Important point

**Session-based authentication can still use cookies.**

These concepts aren't alternatives:

```text
Session + Cookie
```

is a very common authentication architecture.

# 4. Cookies

A cookie is a small piece of data associated with a website/domain that browsers can send with HTTP requests.

Authentication systems commonly use cookies to store:

* Session IDs
* Access tokens
* Refresh tokens

### Important cookie attributes

#### `HttpOnly`

```text
HttpOnly
```

JavaScript cannot directly access the cookie.

This helps reduce the impact of some XSS attacks stealing authentication cookies.

---

#### `Secure`

```text
Secure
```

Cookie is sent only over HTTPS.

---

#### `SameSite`

Controls when cookies are sent in cross-site requests.

Common values:

```text
Strict
Lax
None
```

`SameSite` is particularly relevant to **CSRF protection**.

---

### Example

```http
Set-Cookie: sessionId=abc123; HttpOnly; Secure; SameSite=Lax
```

### Interview point

> For sensitive authentication cookies, `HttpOnly`, `Secure`, and an appropriate `SameSite` policy are important security controls.

---

# 5. CSRF

**CSRF = Cross-Site Request Forgery**

The attacker tricks a user's browser into sending an authenticated request to your application.

The key problem is:

> Browsers automatically attach cookies to requests, including requests initiated from another site under conditions where the cookie is allowed.

Example:

```text
User logged into bank.com
        ↓
Visits malicious-site.com
        ↓
Malicious site causes request to bank.com
        ↓
Browser automatically includes bank cookie
        ↓
Bank may think request came from the user
```

### Prevention

Common techniques include:

* `SameSite` cookies
* CSRF tokens
* Checking `Origin`/`Referer` where appropriate
* Avoiding unsafe state-changing operations via GET

### CSRF token concept

Server gives the application a token:

```text
Server → CSRF token
```

Client sends it with state-changing requests:

```http
POST /transfer

X-CSRF-Token: abc123
```

Server validates it.

### Important distinction

CSRF is especially relevant to **cookie-based authentication** because browsers automatically send cookies.

# 6. XSS Prevention

**XSS = Cross-Site Scripting**

An attacker manages to inject malicious JavaScript into a page that other users view.

Example conceptually:

```html
<script>
  maliciousCode()
</script>
```

### Why is XSS dangerous?

Injected JavaScript can potentially:

* Read page data
* Perform actions as the user
* Access tokens stored in JavaScript-accessible storage
* Modify the UI
* Send sensitive information to an attacker

### React protection

React escapes values rendered through JSX by default.

For example:

```jsx
<div>{userInput}</div>
```

React treats `userInput` as text rather than directly interpreting it as HTML.

### Be careful with

```jsx
dangerouslySetInnerHTML
```

If you render untrusted HTML without proper sanitization, you can introduce XSS.

### Other prevention techniques

* Avoid injecting untrusted HTML
* Sanitize HTML when HTML rendering is genuinely required
* Use Content Security Policy (CSP)
* Keep dependencies updated
* Validate/sanitize data appropriately
* Don't put sensitive tokens where malicious JavaScript can easily access them

# 7. Secure Storage

This is a **very common interview topic**.

You may hear:

> "Should we store JWT in localStorage?"

There isn't a one-line universal answer, but you should understand the tradeoff.

---

## localStorage

```javascript
localStorage.setItem("token", token);
```

### Advantage

Easy to use.

### Problem

JavaScript can access it:

```javascript
localStorage.getItem("token");
```

Therefore, if your application has an XSS vulnerability, malicious JavaScript may be able to steal a token stored there.

So:

> **localStorage is accessible to JavaScript and therefore an attractive target during XSS.**

---

## sessionStorage

Similar security consideration:

```javascript
sessionStorage.setItem("token", token);
```

It generally lasts only for the browser tab/session lifecycle, but **JavaScript can still access it**.

So it doesn't solve the XSS problem.

---

## HttpOnly Cookie

A common secure architecture is:

```text
Authentication
     ↓
HttpOnly + Secure Cookie
     ↓
Browser
     ↓
Automatically sent to server
```

JavaScript cannot read an `HttpOnly` cookie.

This makes token theft via JavaScript harder.

But remember:

> **HttpOnly does NOT magically prevent XSS.**

And cookie-based authentication requires appropriate **CSRF defenses**, such as `SameSite` and/or CSRF tokens depending on the architecture.

# 🔥 Most Important Comparisons

## JWT vs Session

> **JWT:** authentication information can be represented in a token that the server validates.
> **Session:** server maintains authentication state and the client usually sends a session identifier.

Don't say:

> "JWT is stateless, sessions are stateful."

That's a useful simplification, but JWT-based systems can still maintain server-side state, especially around refresh tokens, revocation, etc.

---

## OAuth vs JWT

> **OAuth is an authorization framework; JWT is a token format.**

OAuth can use JWTs, but OAuth ≠ JWT.

---

## Cookie vs localStorage

| HttpOnly Cookie                           | localStorage                                |
| ----------------------------------------- | ------------------------------------------- |
| JS cannot directly access                 | JS can access                               |
| Automatically sent with matching requests | Must manually attach                        |
| Can use Secure                            | No equivalent HttpOnly protection           |
| Need CSRF considerations                  | XSS token theft is a major concern          |
| Common for session/refresh auth           | Convenient but riskier for sensitive tokens |

---

## CSRF vs XSS

This distinction is **very interview-worthy**.

### XSS

> Attacker executes malicious JavaScript in your application's context.

```text
Malicious script
      ↓
Runs in your app
```

### CSRF

> Attacker causes the victim's browser to make an unwanted authenticated request.

```text
Malicious website
      ↓
Victim's browser
      ↓
Authenticated request to target site
```

Simple memory trick:

```text
XSS  → "Run my script"

CSRF → "Make the browser send my request"
```

# ⭐ 10 Questions You Should Be Ready For

### 1. What is JWT?

A token format containing claims that can be signed and validated by the server.

### 2. Is JWT encrypted?

Not necessarily. A normal JWT is typically **encoded and signed**, not encrypted.

### 3. JWT vs session?

JWT commonly carries claims in the token; session authentication commonly stores state server-side and uses a session identifier.

### 4. What is OAuth?

An authorization framework that allows applications to obtain delegated access to resources.

### 5. OAuth vs JWT?

OAuth is a protocol/framework; JWT is a token format.

### 6. What is HttpOnly?

Prevents client-side JavaScript from directly reading the cookie.

### 7. What is Secure cookie?

It instructs the browser to send the cookie only over HTTPS.

### 8. What is CSRF?

An attacker causes a user's browser to make an unwanted authenticated request.

### 9. How do you prevent XSS in React?

> React escapes JSX values by default. Avoid unsafe HTML injection, sanitize required HTML, be careful with `dangerouslySetInnerHTML`, use CSP, and keep dependencies secure.

### 10. Where should JWT be stored?

There isn't one universal answer, but for browser applications, **HttpOnly + Secure cookies are commonly preferred for sensitive authentication credentials** because JavaScript cannot directly read them. If cookies are used, CSRF defenses must also be considered.
