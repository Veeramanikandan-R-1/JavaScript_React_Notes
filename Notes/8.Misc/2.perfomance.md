# Web Performance — React Interview Notes

For a **5-year React developer**, focus on **what problem each optimization solves, how it works, and when to use it**.

---

## 1. Lazy Loading

**Lazy loading = load something only when it is actually needed.**

Instead of loading every component on initial page load, load heavy components when the user needs them.

### React `lazy` + `Suspense`

```jsx
import { lazy, Suspense } from "react";

const Dashboard = lazy(() => import("./Dashboard"));

function App() {
  return (
    <Suspense fallback={<div>Loading...</div>}>
      <Dashboard />
    </Suspense>
  );
}
```

Instead of:

```jsx
import Dashboard from "./Dashboard";
```

the Dashboard becomes a **separate chunk**.

### Route-level lazy loading

This is one of the most useful patterns in large React applications.

```jsx
const Users = lazy(() => import("./pages/Users"));
const Reports = lazy(() => import("./pages/Reports"));
const Settings = lazy(() => import("./pages/Settings"));
```

```text
Initial load
   ↓
Home chunk

User visits Reports
   ↓
Reports chunk loaded
```

### Lazy-load other resources

Can also apply to:

* Images
* Videos
* Components
* Routes
* Heavy libraries

```html
<img src="image.webp" loading="lazy" alt="Product" />
```

### When NOT to lazy load

Don't lazy-load everything.

Avoid lazy loading:

* Critical above-the-fold content
* Tiny components
* Components needed immediately

**Interview:** Lazy loading reduces **initial JavaScript/network work**, improving initial load performance.

# 2. Bundle Splitting / Code Splitting

**Bundle splitting = divide a large JavaScript bundle into smaller chunks.**

Instead of:

```text
app.js → 5 MB
```

you can have:

```text
main.js       → 500 KB
dashboard.js  → 300 KB
reports.js    → 400 KB
admin.js      → 500 KB
```

Only required chunks are loaded.

### Dynamic import

```jsx
const Reports = lazy(() => import("./Reports"));
```

This generates a separate chunk during the build.

### Route-based splitting

Usually the **first optimization to consider** for a large React application.

```text
/
 ├── Home
 ├── Users
 ├── Reports
 └── Admin
```

Load:

```text
Home → Home chunk
Users → Users chunk
Reports → Reports chunk
```

### Component/library splitting

```js
const Chart = lazy(() => import("./HeavyChart"));
```

Useful for:

* Charts
* Editors
* Maps
* PDF viewers
* Large UI components

### Lazy Loading vs Bundle Splitting

They are related but not identical.

> **Code splitting creates separate chunks. Lazy loading determines when those chunks/resources are loaded.**

# 3. Tree Shaking

**Tree shaking = removing unused code from the production bundle.**

Example:

```js
// utils.js
export const add = (a, b) => a + b;

export const subtract = (a, b) => a - b;
```

```js
import { add } from "./utils";
```

If `subtract` isn't used, a production build may remove it.

```text
Before:
add + subtract

After:
add
```

### Works best with ES Modules

```js
import { add } from "./utils";
export { add };
```

Because imports/exports are statically analyzable.

### CommonJS

```js
const utils = require("./utils");
```

is generally harder for bundlers to analyze for tree shaking.

### How to improve tree shaking

Prefer:

```js
import { debounce } from "lodash-es";
```

rather than unnecessarily importing a huge library.

Also avoid importing an entire library when only one feature is required, when the library/build supports more granular imports.

### Important

Tree shaking generally happens during **production builds**, not normal development.

# 4. Image Optimization

Images are often one of the largest contributors to page weight.

## Use modern formats

Prefer:

```text
AVIF
WebP
```

when appropriate instead of unnecessarily large JPEG/PNG files.

Example:

```html
<img
  src="/images/product.webp"
  alt="Product"
/>
```

---

## Responsive Images

Don't send a 2000px image to a mobile device that displays it at 300px.

```html
<img
  src="product-800.webp"
  srcset="
    product-400.webp 400w,
    product-800.webp 800w,
    product-1200.webp 1200w
  "
  sizes="(max-width: 600px) 100vw, 50vw"
  alt="Product"
/>
```

Browser chooses an appropriate resource.

---

## Lazy-load non-critical images

```html
<img
  src="/gallery.webp"
  loading="lazy"
  alt="Gallery"
/>
```

Don't lazy-load the main **LCP image** blindly.

---

## Specify dimensions

```html
<img
  src="/product.webp"
  width="800"
  height="600"
  alt="Product"
/>
```

This helps reserve layout space and reduces **CLS**.

---

## Compress images

Reduce:

```text
Resolution
+
File size
+
Unnecessary metadata
```

without noticeably reducing visual quality.

### React example

```jsx
<img
  src={product.thumbnail}
  loading="lazy"
  width={300}
  height={200}
  alt={product.name}
/>
```

### Interview checklist

```text
✓ WebP / AVIF
✓ Compression
✓ Responsive images
✓ srcset / sizes
✓ Lazy loading
✓ Correct dimensions
✓ CDN/image transformation
✓ Don't send unnecessarily huge images
```

# 5. Lighthouse

**Lighthouse is a performance/auditing tool available through Chrome DevTools and other environments.**

It audits areas such as:

* Performance
* Accessibility
* Best Practices
* SEO

It provides metrics, diagnostics and opportunities for improvement.

### Typical workflow

```text
Open Chrome DevTools
       ↓
Lighthouse
       ↓
Run audit
       ↓
Check metrics
       ↓
Fix bottlenecks
       ↓
Run again
```

### Useful diagnostics

Lighthouse can highlight things such as:

* Large JavaScript
* Render-blocking resources
* Image optimization opportunities
* Unused JavaScript/CSS
* Poor caching
* Long main-thread work
* Layout shifts

### Important

A Lighthouse score is **not the same thing as real-user performance**.

Lab testing can differ from real-world users because of:

* Device
* Network
* CPU
* Location
* Cache state

So combine Lighthouse with **real-user monitoring (RUM)** where possible.

# 6. Core Web Vitals

Core Web Vitals are Google's key user-experience performance metrics.

The important current metrics are:

### 1. LCP — Largest Contentful Paint

Measures how quickly the **largest relevant content element** becomes visible.

Usually:

```text
Hero image
Large heading
Main content block
```

Good target:

```text
≤ 2.5 seconds
```

### Improve LCP

* Optimize hero image
* Preload critical resources when appropriate
* Reduce server response time
* Reduce render-blocking resources
* Reduce JavaScript
* Use CDN
* Improve caching

---

## 2. INP — Interaction to Next Paint

Measures **interaction responsiveness**.

It looks at how quickly the page responds visually after user interactions.

Good:

```text
≤ 200 ms
```

Poor INP can be caused by:

```text
Click
 ↓
Huge JS task
 ↓
React rendering
 ↓
UI finally updates
```

### Improve INP

* Reduce JavaScript
* Break up long tasks
* Avoid unnecessary React renders
* Optimize expensive calculations
* Use `useMemo`/`useCallback` only where they actually help
* Use `useTransition` for appropriate non-urgent updates
* Virtualize large lists

---

## 3. CLS — Cumulative Layout Shift

Measures unexpected movement of page content.

Bad:

```text
Page loads

[Article]

        ↓ image loads

[Image]

Article suddenly moves ↓
```

### Prevent CLS

Reserve space:

```html
<img
  src="banner.webp"
  width="1200"
  height="600"
  alt="Banner"
/>
```

Also consider:

* Explicit image/video dimensions
* Avoid inserting content above existing content unexpectedly
* Reserve space for ads/embeds
* Avoid layout changes caused by late-loading fonts

---

### Core Web Vitals Summary

| Metric  | Measures                   |    Good |
| ------- | -------------------------- | ------: |
| **LCP** | Loading performance        |  ≤ 2.5s |
| **INP** | Interaction responsiveness | ≤ 200ms |
| **CLS** | Visual stability           |   ≤ 0.1 |

**Interview note:** FID has been replaced by **INP** as the Core Web Vital for responsiveness.

# 7. Caching

**Caching = storing resources so they don't need to be downloaded/generated again unnecessarily.**

Common layers:

```text
Browser Cache
      ↓
CDN Cache
      ↓
Server/Application Cache
      ↓
Database Cache
```

---

## Browser HTTP caching

Server can provide:

```http
Cache-Control: max-age=31536000
```

Browser can reuse the resource for the specified period.

### Immutable hashed assets

Production builds commonly generate:

```text
main.a82f91.js
styles.71bc21.css
```

Then you can cache them aggressively:

```http
Cache-Control: public, max-age=31536000, immutable
```

When content changes:

```text
main.a82f91.js
       ↓
main.b17c20.js
```

The URL changes, so the browser fetches the new file.

---

## Cache-Control

Common directives:

```http
Cache-Control: no-cache
Cache-Control: no-store
Cache-Control: max-age=3600
Cache-Control: public, max-age=31536000, immutable
```

### Important distinction

`no-cache` does **not** mean "don't store".

It generally means:

> Store it if appropriate, but revalidate before using it as a fresh response.

`no-store` means:

> Don't store the response.

---

## ETag

Server can send:

```http
ETag: "abc123"
```

Browser later sends:

```http
If-None-Match: "abc123"
```

If unchanged:

```http
304 Not Modified
```

This avoids retransmitting the full resource.

# 8. CDN

**CDN = Content Delivery Network.**

A CDN distributes/cache content across geographically distributed edge locations.

Without CDN:

```text
User → Origin Server
```

With CDN:

```text
User
 ↓
Nearest CDN Edge
 ↓
Cached resource
```

### Benefits

* Lower latency
* Faster static asset delivery
* Reduced origin server load
* Better scalability
* Can provide caching/compression/security features

Good candidates:

```text
JS
CSS
Images
Fonts
Videos
Static files
```

---

## CDN Cache Hit

```text
User
 ↓
CDN
 ↓
Cache HIT
 ↓
Return file
```

No origin request required.

### Cache Miss

```text
User
 ↓
CDN
 ↓
Cache MISS
 ↓
Origin Server
 ↓
CDN caches response
 ↓
User
```

# 🔥 Interview Questions You Should Know

### 1. Lazy loading vs code splitting?

> **Code splitting** divides the application into multiple chunks. **Lazy loading** controls when a chunk/resource is actually loaded.

---

### 2. How would you reduce initial bundle size?

```text
1. Analyze bundle
2. Route-based code splitting
3. Lazy load heavy components
4. Tree shaking
5. Remove unused dependencies
6. Replace heavy libraries
7. Optimize imports
8. Compress/minify assets
9. Serve compressed responses
```

---

### 3. How would you improve LCP?

```text
Optimize critical/hero image
        +
Reduce server response time
        +
Remove render-blocking resources
        +
Reduce initial JS
        +
Preload truly critical resources
        +
CDN/cache
```

---

### 4. How would you fix CLS?

```text
Reserve image dimensions
Avoid injecting content above existing content
Reserve space for dynamic content
Handle fonts carefully
```

---

### 5. How would you improve INP in React?

```text
Avoid unnecessary renders
        +
Reduce expensive event handlers
        +
Split long JS tasks
        +
Virtualize large lists
        +
Use transitions for non-urgent updates
        +
Lazy-load heavy functionality
```

---

### 6. Does lazy loading always improve performance?

**No.**

If you lazy-load something required immediately, you may introduce an additional network request and delay rendering.

> Lazy-load **non-critical/heavy resources**, not everything.

---

### 7. What is the difference between caching and CDN?

> **Caching** is the general technique of storing reusable resources. A **CDN** is a distributed network infrastructure that can cache and deliver those resources from locations closer to users.

## ⭐ Senior-Level Performance Mental Model

When asked **"How will you optimize a React application?"**, structure your answer like this:

```text
1. Measure
   ↓
Lighthouse / DevTools / RUM

2. Network
   ↓
CDN / HTTP caching / compression

3. JavaScript
   ↓
Code splitting / lazy loading / tree shaking

4. React
   ↓
Avoid unnecessary renders
Memoization where justified
Virtualization
Transitions where appropriate

5. Assets
   ↓
Image optimization
Fonts
CSS

6. Rendering
   ↓
Fix LCP / INP / CLS

7. Verify
   ↓
Measure again
```

**Key principle:** **Don't optimize based on assumptions. Measure first → identify bottleneck → optimize → measure again.**
