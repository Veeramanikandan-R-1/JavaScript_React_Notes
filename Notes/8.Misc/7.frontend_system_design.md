# Frontend System Design — Senior-Level Interview Notes

For a **6-year React developer**, this section is more important than memorizing individual definitions. Interviewers usually want to know:

> **"How would you structure and scale a React application, and why would you make those choices?"**

You don't need to go very deep here, but you should be able to explain the **trade-offs**.

---

# 1. Component Architecture

Component architecture means deciding **how to divide the UI and behavior into reusable components**.

Instead of one huge component:

```text
App
 └── Everything
```

you break it down:

```text
App
 ├── Header
 ├── Sidebar
 ├── Dashboard
 │    ├── StatsCard
 │    ├── Chart
 │    └── UserList
 └── Footer
```

### Good component

Ideally has:

* Clear responsibility
* Reusable where appropriate
* Minimal unnecessary coupling
* Predictable props/API

### Senior-level consideration

Don't blindly make everything reusable.

> **Extract a component when it improves readability, reuse, isolation, or maintainability.**

Over-abstraction can make a codebase harder to understand.

---

# 2. Folder Organization

There isn't one universally correct folder structure.

Two common approaches:

### Type-based

```text
src/
├── components/
├── hooks/
├── services/
├── utils/
├── pages/
└── store/
```

### Feature-based

```text
src/
├── features/
│   ├── auth/
│   │   ├── components/
│   │   ├── hooks/
│   │   ├── api/
│   │   └── types/
│   │
│   └── users/
│       ├── components/
│       ├── hooks/
│       └── api/
│
├── shared/
└── app/
```

For a **large application**, feature-based organization is often easier to scale.

### Interview answer

> "For a small application, a simple type-based structure is fine. As the application grows, I prefer feature-oriented organization so related UI, hooks, API logic, and tests stay close together."

# 3. State Management Strategy

Don't put everything into global state.

First identify the type of state.

### Local UI state

```text
Modal open/closed
Input value
Selected tab
```

Use:

```js
useState
useReducer
```

### Server state

```text
Users
Products
Orders
API responses
```

Consider:

```text
TanStack Query
SWR
Apollo
```

### Global client state

```text
Theme
Authentication state
Shopping cart
Global UI state
```

Could use:

```text
Context
Redux
Zustand
etc.
```

### Key principle

```text
Local state → keep local

Server state → data-fetching/cache solution

Global shared state → global store/context when necessary
```

**Senior-level point:**

> Don't make state global just because multiple components currently need it. First understand its ownership and lifetime.

# 4. Large Form Handling

Large forms can become difficult because of:

* Many fields
* Validation
* Conditional fields
* Dependent fields
* Performance
* Error handling
* Server validation

Typical approach:

```text
Form
 ├── Personal Details
 ├── Address
 ├── Payment
 └── Preferences
```

Use a form library when complexity justifies it, such as:

* React Hook Form
* Formik

### Important considerations

* Centralized validation
* Field-level validation
* Server-side validation
* Avoid unnecessary re-renders
* Handle dirty/touched state
* Handle submit/loading/error states

### Interview answer

> "For a large form, I'd use a dedicated form library, schema-based validation where appropriate, isolate field components, and avoid causing the entire form to re-render on every keystroke."

# 5. Data Fetching Strategy

Don't fetch data randomly from components.

Think about:

```text
Where?
When?
How often?
What happens during loading?
What happens on failure?
Should it be cached?
```

Typical approach:

```text
Component
    ↓
Custom Hook / Query
    ↓
API layer
    ↓
Backend
```

Example concept:

```js
const { data, isLoading, error } = useUsers();
```

Instead of putting all API logic directly inside the UI.

### Consider

* Loading states
* Error states
* Retries
* Cancellation
* Cache
* Refetching
* Pagination
* Authentication
* Optimistic updates

# 6. Caching

Caching means **reusing previously fetched data instead of requesting it again unnecessarily**.

Example:

```text
First visit
   ↓
API request
   ↓
Cache data

Second visit
   ↓
Use cached data
   ↓
Optional background refresh
```

Popular React data-fetching solutions:

```text
TanStack Query
SWR
Apollo Client
```

### Important concepts

* Cache key
* Cache lifetime
* Stale data
* Refetch
* Invalidation

Example:

```text
users?page=1
```

can be cached separately from:

```text
users?page=2
```

### Senior-level question

> "When should the cache be invalidated?"

For example, after creating a user, the cached users list may need to be updated or invalidated.

# 7. Pagination

Pagination means loading data in **smaller chunks/pages** rather than fetching everything.

Example:

```text
Page 1 → 1–20
Page 2 → 21–40
Page 3 → 41–60
```

API:

```http
GET /users?page=2&limit=20
```

### Advantages

* Less data transferred
* Faster initial load
* Lower memory usage
* Better backend scalability

### Common types

**Offset pagination**

```text
?page=2&limit=20
```

**Cursor pagination**

```text
?cursor=abc123&limit=20
```

Cursor pagination is often better for datasets that change frequently.

---

### Pagination — Short Example

Suppose the API has **100 users**, but we only want to load **10 at a time**.

### API

```http
GET /api/users?page=1&limit=10
```

Response:

```json
{
  "data": ["user1", "user2", "..."],
  "page": 1,
  "limit": 10,
  "total": 100
}
```

Then the next page:

```http
GET /api/users?page=2&limit=10
```

```text
Page 1 → users 1–10
Page 2 → users 11–20
Page 3 → users 21–30
...
```

### React example

```jsx
const [page, setPage] = useState(1);

const { data } = useQuery({
  queryKey: ["users", page],
  queryFn: () => fetch(`/api/users?page=${page}&limit=10`)
    .then(res => res.json())
});

return (
  <>
    <UserList users={data?.data} />

    <button
      disabled={page === 1}
      onClick={() => setPage(page - 1)}
    >
      Previous
    </button>

    <button
      disabled={page * 10 >= data?.total}
      onClick={() => setPage(page + 1)}
    >
      Next
    </button>
  </>
);
```

### Interview one-liner

> **Pagination means fetching data in smaller chunks instead of loading the entire dataset at once, usually using page/limit or cursor-based APIs.**

# 8. Infinite Scroll

Instead of showing:

```text
Previous | 1 | 2 | 3 | Next
```

you load more when the user reaches the bottom.

```text
Initial data
     ↓
Scroll
     ↓
Load more
     ↓
Append data
     ↓
Scroll
     ↓
Load more
```

Common implementation:

**Intersection Observer**

```text
User reaches sentinel element
        ↓
Intersection Observer
        ↓
Fetch next page
```

### Important considerations

* Loading indicator
* Prevent duplicate requests
* End-of-list detection
* Error retry
* Preserve scroll position
* Virtualization for very large lists

# 9. Debouncing

**Debouncing = wait until the user stops triggering an event before executing the function.**

Example: search box.

Without debounce:

```text
R → API
Re → API
Rea → API
Reac → API
React → API
```

With debounce:

```text
R
Re
Rea
Reac
React
   ↓
wait
   ↓
API request
```

Typical use cases:

* Search
* Autocomplete
* Input validation
* Resize-related work

### Simple definition

> **Debounce = execute after the activity stops for a specified time.**

### Debounce — Good Real-World Example

**Search/autocomplete** is the most common example.

Without debounce, if the user types:

```text
r → API call
re → API call
rea → API call
reac → API call
react → API call
```

That's **5 API calls**.

With debounce, we wait until the user **stops typing for 500ms**:

```text
r
re
rea
reac
react
      ↓ wait 500ms
      ↓
   API call
```

### Simple JavaScript Example

```js
function debounce(fn, delay) {
  let timer;

  return function (...args) {
    clearTimeout(timer);

    timer = setTimeout(() => {
      fn(...args);
    }, delay);
  };
}

const search = debounce((value) => {
  console.log("API call:", value);
}, 500);

search("r");
search("re");
search("rea");
search("react");
```

Only the **last call** executes if the calls happen within the 500ms window.

### React Example

```jsx
const handleSearch = debounce((value) => {
  fetch(`/api/search?q=${value}`);
}, 500);

<input
  onChange={(e) => handleSearch(e.target.value)}
/>
```

### Interview one-liner

> **Debouncing delays function execution until the user stops triggering the event for a specified period. It's commonly used for search inputs to avoid unnecessary API calls.**

**Easy way to remember:**

> **Debounce = "Wait until they stop."**

Debounce example:

```js
import React, { useState, useEffect, useMemo } from 'react';

const App = () => {
  const [searchVal, setSearchVal] = useState('');
  const fetchApi = () => {
    console.log('api call');
  };

  const debounce = (fn, delay) => {
    let timer;
    return function (...args) {
      clearTimeout(timer);
      timer = setTimeout(() => {
        fn(...args);
      }, delay);
    };
  };

  const debouncedFetch = useMemo(() => debounce(fetchApi, 2000), []);

  useEffect(() => {
    debouncedFetch();
  }, [searchVal]);
  const changeHanlder = (e) => {
    setSearchVal(e.target.value);
  };
  return (
    <div>
      <input name="search" onChange={changeHanlder} value={searchVal} />
    </div>
  );
};

export default App;
```

debounce simple implementation using useEffect alone

```js
import React, { useState, useEffect, useMemo } from 'react';

const App = () => {
  const [searchVal, setSearchVal] = useState('');
  const fetchApi = () => {
    console.log('api call');
  };

  useEffect(() => {
    let timer = setTimeout(() => {
      fetchApi();
    }, 2000);
    return () => {
      clearTimeout(timer);
    };
  }, [searchVal]);
  const changeHanlder = (e) => {
    setSearchVal(e.target.value);
  };
  return (
    <div>
      <input name="search" onChange={changeHanlder} value={searchVal} />
    </div>
  );
};

export default App;
```

# 10. Throttling

**Throttling = limit how often a function can execute.**

Example:

```text
Scroll event
↓
↓
↓
↓
↓
```

Instead of executing hundreds of times:

```text
Execute
   ↓
wait
   ↓
Execute
   ↓
wait
```

Typical use cases:

* Scroll
* Mouse movement
* Resize
* Continuous user interactions

### Debounce vs Throttle

```text
Debounce
→ Wait until activity stops

Throttle
→ Execute at most once per interval
```

Easy example:

**Search input → Debounce**

**Scroll event → Throttle**

throttling example:

Sure. A very common and easy-to-understand **throttling example in React is handling scroll events**.

### Throttling

> **Throttle = execute a function at most once in a given time period.**

For example, even if the user scrolls 100 times in 1 second, we might want our function to execute only once every 1 second.

```jsx
import React, { useEffect, useState } from 'react';

const App = () => {
  const [scrollY, setScrollY] = useState(0);

  const throttle = (fn, delay) => {
    let lastCall = 0;

    return function (...args) {
      const now = Date.now();

      if (now - lastCall >= delay) {
        lastCall = now;
        fn(...args);
      }
    };
  };

  useEffect(() => {
    const handleScroll = throttle(() => {
      console.log('Scroll event');
      setScrollY(window.scrollY);
    }, 1000);

    window.addEventListener('scroll', handleScroll);

    return () => {
      window.removeEventListener('scroll', handleScroll);
    };
  }, []);

  return (
    <div style={{ height: '200vh', padding: '20px' }}>
      <h1>Scroll Y: {scrollY}</h1>
    </div>
  );
};

export default App;
```

### How it works

Without throttle:

```text
Scroll → API
Scroll → API
Scroll → API
Scroll → API
Scroll → API
Scroll → API
...
```

With **1 second throttle**:

```text
Scroll → API
  ↓
  ↓
  ↓  ignored
  ↓
  ↓  ignored
1 second
  ↓
Scroll → API
  ↓
  ↓  ignored
1 second
  ↓
Scroll → API
```

So the function runs **at most once every 1 second**.

### Debounce vs Throttle

This is a very common interview question:

| Debounce                       | Throttle                        |
| ------------------------------ | ------------------------------- |
| Waits until activity **stops** | Runs during continuous activity |
| Resets timer on every event    | Limits execution frequency      |
| Search input                   | Scroll                          |
| API search                     | Mouse movement                  |
| "Run after user stops typing"  | "Run at most once per second"   |

**Easy way to remember:**

> 🔵 **Debounce:** "Wait until you're done."
> 🟢 **Throttle:** "Slow down how often I run."**

# 11. Error Boundaries

React Error Boundaries catch **rendering errors in a component tree** and show fallback UI instead of crashing the entire UI tree.

Conceptually:

```text
ErrorBoundary
    |
    +-- Header
    +-- Dashboard
         |
         +-- Chart 💥
```

Instead of the entire application becoming unusable:

```text
ErrorBoundary
     ↓
Fallback UI
"Something went wrong"
```

### Important limitation

Error boundaries don't catch every type of error.

They are mainly for errors during:

* Rendering
* Lifecycle methods
* Constructors of child components

They don't automatically handle things such as:

* Event handler errors
* Most async callback errors
* Server/API errors

Those need separate handling.

### Senior-level usage

Place boundaries strategically:

```text
App
 ├── Global Error Boundary
 ├── Dashboard Boundary
 └── Feature Boundary
```

# 12. Feature Flags

Feature flags allow you to **turn functionality on/off without deploying different code versions**.

Example:

```js
if (featureFlags.newDashboard) {
  return <NewDashboard />;
}

return <OldDashboard />;
```

Useful for:

* Gradual rollout
* A/B testing
* Beta features
* Kill switches
* Release safety

Example:

```text
100% users → old feature

         ↓

10% users → new feature

         ↓

50% users → new feature

         ↓

100% users → new feature
```

### Senior-level consideration

Feature flags need lifecycle management.

Don't leave hundreds of old flags forever.

# 13. Internationalization — i18n

**i18n = internationalization.**

It means designing the application so it can support multiple languages/locales.

Instead of:

```jsx
<h1>Hello</h1>
```

you use a translation key:

```jsx
<h1>{t("welcome")}</h1>
```

Translations:

```text
en:
welcome = "Hello"

fr:
welcome = "Bonjour"

de:
welcome = "Hallo"
```

### i18n also involves

* Date formatting
* Number formatting
* Currency
* Pluralization
* Text direction
* Locale-specific formatting

### RTL

Languages such as Arabic and Hebrew require right-to-left layouts.

So don't design the UI assuming everything is always LTR.

# 14. Accessibility

**Accessibility (a11y) = making applications usable by people with different abilities.**

Important areas:

### Semantic HTML

Prefer:

```html
<button>Save</button>
```

over:

```html
<div onclick="save()">Save</div>
```

### Keyboard navigation

Users should be able to navigate without a mouse.

### Screen readers

Use meaningful:

* Labels
* Headings
* Alt text
* Semantic elements

### ARIA

Use ARIA when native HTML semantics aren't sufficient.

Don't use ARIA as a replacement for proper HTML.

### Important areas

```text
Keyboard navigation
Screen readers
Color contrast
Focus management
Forms and labels
Semantic HTML
Accessible errors
```

### Interview answer

> "I treat accessibility as part of component design rather than something added at the end."

# 15. Theming

Theming means supporting different visual styles through a centralized design system.

For example:

```text
Theme
 ├── Colors
 ├── Typography
 ├── Spacing
 ├── Borders
 └── Shadows
```

Instead of hardcoding:

```css
color: #123456;
```

use design tokens:

```css
color: var(--color-primary);
```

This makes it easier to support:

```text
Default theme
Dark theme
High contrast theme
Brand A
Brand B
```

# 16. Dark Mode

Dark mode is essentially a theme where the UI uses a dark color scheme.

A common approach:

```css
:root {
  --background: white;
  --text: black;
}

[data-theme="dark"] {
  --background: black;
  --text: white;
}
```

Then:

```css
body {
  background: var(--background);
  color: var(--text);
}
```

### Important

You should consider the user's OS preference:

```css
@media (prefers-color-scheme: dark) {
  /* dark theme */
}
```

Also consider:

* Persisting user preference
* System preference
* Contrast
* Images/icons
* Third-party components

# 17. Micro Frontends — Basics

**Micro Frontends = splitting a large frontend application into independently developed/deployed frontend parts.**

Instead of:

```text
One Huge Frontend
      |
   Everything
```

you might have:

```text
                 Shell
                  |
       +----------+----------+
       |          |          |
     Users      Orders    Payments
       |          |          |
     Team A     Team B     Team C
```

Different teams can own different parts.

### Advantages

* Independent team ownership
* Independent deployments
* Large application can be split into smaller domains
* Teams can potentially evolve parts independently

### Disadvantages

* More architectural complexity
* Duplicate dependencies
* Cross-app communication
* Consistent UX/design becomes harder
* Performance concerns
* Deployment/versioning complexity

### When to use?

Don't use micro frontends just because the application is large.

They're more appropriate when you have:

* Large organization
* Multiple autonomous teams
* Clearly separated business domains
* Need for independent deployment

### Interview answer

> "Micro Frontends apply microservice-like team and deployment boundaries to the frontend. They can help large organizations scale development, but introduce significant runtime, dependency, communication, and UX complexity."

# 🔥 Most Important Senior-Level Trade-offs

For system-design interviews, remember these:

### State

```text
Local UI state
      ↓
Keep local

Server state
      ↓
Use query/cache solution

Shared client state
      ↓
Context/store when necessary
```

### Pagination vs Infinite Scroll

```text
Pagination
→ Better navigation
→ Easy to bookmark/share
→ Good for tables/admin systems

Infinite scroll
→ Good for feeds/social/content browsing
→ Can become difficult for navigation/accessibility
```

### Debounce vs Throttle

```text
Debounce
→ Search/autocomplete

Throttle
→ Scroll/mouse movement
```

### Component architecture

> Don't optimize for maximum reuse. Optimize for **clear boundaries and maintainability**.

### Caching

> Cache server data, but have a clear strategy for **staleness, invalidation, and updates**.

### Micro Frontends

> Use them to solve **organizational/team scaling problems**, not merely because the codebase is large.
