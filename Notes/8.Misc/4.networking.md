
## 1. HTTP

**HTTP = HyperText Transfer Protocol**

It's the protocol used for communication between a client (browser) and server.

Typical React application:

```text
React App
   ↓ HTTP Request
Backend API
   ↓ HTTP Response
React App
```

Example:

```http
GET /api/users
```

### Common HTTP methods

| Method | Purpose                   |
| ------ | ------------------------- |
| GET    | Retrieve data             |
| POST   | Create/send data          |
| PUT    | Replace/update resource   |
| PATCH  | Partially update resource |
| DELETE | Delete resource           |

### Important

HTTP itself doesn't encrypt the data.

That's where **HTTPS** comes in.

---

# 2. HTTPS

**HTTPS = HTTP + TLS encryption**

It protects communication between browser and server.

```text
Browser
   ⇅
 HTTPS / TLS
   ⇅
Server
```

Provides:

* Encryption
* Data integrity
* Server authentication

Example:

```text
http://example.com
        ↓
https://example.com
```

For modern applications, APIs should generally be accessed over HTTPS.

### Remember

> **HTTP = communication protocol**
> **HTTPS = HTTP protected by TLS**

# 3. REST

**REST = Representational State Transfer**

It's an architectural style commonly used for APIs.

Resources are typically represented using URLs.

Example:

```text
GET    /users
GET    /users/123
POST   /users
PATCH  /users/123
DELETE /users/123
```

Think:

```text
/users       → collection
/users/123   → specific resource
```

### REST characteristics

Common REST APIs are:

* Resource-oriented
* Stateless
* HTTP-method based
* Usually return JSON

Example response:

```json
{
  "id": 123,
  "name": "John"
}
```

### Interview point

> REST is an API architectural style, not a specific protocol.

---
You **can technically send data with a GET request in some ways**, but you generally **shouldn't use GET for operations that create/change data**.

### GET is meant for reading

```http
GET /users/123
```

Meaning:

> "Give me user 123."

GET should be **safe and idempotent** — calling it multiple times shouldn't change server state.

---

### POST is meant for sending/creating data

```http
POST /users
Content-Type: application/json

{
  "name": "John"
}
```

Meaning:

> "Create a new user with this data."

---

### Why not GET for POST-like operations?

**1. GET parameters appear in the URL**

```http
GET /login?username=john&password=secret
```

This is bad because URLs can end up in:

* Browser history
* Server/proxy logs
* Analytics logs
* Referer information

---

**2. GET can be cached**

Browsers/proxies can cache GET requests. You don't want something like:

```http
GET /deleteUser?id=123
```

being cached or automatically replayed.

---

**3. GET can be triggered automatically**

Browsers, crawlers, prefetchers, etc. may request GET URLs.

If GET changes data:

```http
GET /deleteAccount
```

that's dangerous.

---

**4. HTTP semantics**

The method communicates the **intent** of the operation:

```text
GET     → Read
POST    → Create/submit
PUT     → Replace
PATCH   → Partial update
DELETE  → Delete
```

### Interview answer

> **"GET is designed for safe retrieval of resources and should not have side effects. POST is intended for submitting data and operations that can change server state. Using GET for mutations also creates security, caching, and accidental-request problems."**

# 4. GraphQL — Basics

**GraphQL is an API query language and runtime.**

Unlike traditional REST where you often have multiple endpoints:

```text
GET /users/123
GET /users/123/posts
GET /users/123/friends
```

GraphQL commonly uses a single endpoint:

```text
POST /graphql
```

The client specifies exactly what data it needs.

Example:

```graphql
query {
  user(id: 123) {
    name
    email
    posts {
      title
    }
  }
}
```

Server returns the requested structure.

### Main advantage

The client can request exactly the fields it needs.

This can reduce:

* **Over-fetching** — getting unnecessary data
* **Under-fetching** — needing multiple requests to get related data

### REST vs GraphQL

| REST                                      | GraphQL                                              |
| ----------------------------------------- | ---------------------------------------------------- |
| Multiple resource endpoints commonly used | Often single endpoint                                |
| Server defines response structure         | Client specifies requested fields                    |
| Easy HTTP caching patterns                | Caching can require more application/client strategy |
| Simple and widely understood              | Flexible querying                                    |
| Can over/under-fetch                      | Helps address over/under-fetching                    |

### Interview answer

> "GraphQL allows clients to request exactly the fields they need through a typed query language, whereas REST typically exposes resource-oriented endpoints with predefined response structures."

# 5. Request Lifecycle

This is **very important for a frontend developer**.

Suppose:

```js
fetch("/api/users");
```

High-level lifecycle:

```text
React
  ↓
fetch()
  ↓
Browser creates HTTP request
  ↓
DNS lookup
  ↓
TCP/TLS connection
  ↓
HTTP request
  ↓
Server
  ↓
Server processes request
  ↓
HTTP response
  ↓
Browser receives response
  ↓
JavaScript processes response
  ↓
React updates UI
```

### HTTP request contains things like:

```text
Method
URL
Headers
Body
```

Example:

```http
POST /api/login HTTP/1.1
Content-Type: application/json

{
  "email": "test@example.com",
  "password": "..."
}
```

Response:

```http
HTTP/1.1 200 OK
Content-Type: application/json

{
  "token": "..."
}
```

### Important frontend concepts

You should understand:

* Request
* Response
* Headers
* Body
* Status code
* Cookies
* Authentication
* CORS

# 6. Status Codes

HTTP status codes tell you the result of a request.

## 2xx — Success

```text
200 OK
```

Request succeeded.

```text
201 Created
```

Resource successfully created.

```text
204 No Content
```

Successful request but no response body.

---

## 3xx — Redirection / caching-related behavior

```text
301 Moved Permanently
302 Found
304 Not Modified
```

`304 Not Modified` is particularly relevant to browser caching.

---

## 4xx — Client-side/request problems

```text
400 Bad Request
```

Invalid request.

```text
401 Unauthorized
```

Authentication is missing/invalid.

Think:

> **"Who are you?"**

```text
403 Forbidden
```

User is authenticated but doesn't have permission.

Think:

> **"I know who you are, but you're not allowed."**

```text
404 Not Found
```

Resource doesn't exist.

```text
409 Conflict
```

Request conflicts with current resource state.

```text
429 Too Many Requests
```

Rate limit exceeded.

---

## 5xx — Server errors

```text
500 Internal Server Error
```

Generic server-side error.

```text
502 Bad Gateway
```

Gateway/proxy received an invalid response.

```text
503 Service Unavailable
```

Server temporarily unavailable.

### Most important distinction

```text
401 → Authentication problem
403 → Authorization/permission problem
```

# 7. Headers

**Headers provide metadata about an HTTP request or response.**

Example request:

```http
Authorization: Bearer <token>
Content-Type: application/json
Accept: application/json
```

### Common request headers

**Authorization**

```http
Authorization: Bearer <token>
```

Used for authentication credentials/tokens.

**Content-Type**

```http
Content-Type: application/json
```

Tells server what format the request body uses.

**Accept**

```http
Accept: application/json
```

Tells server what response formats the client accepts.

---

### Common response headers

```http
Content-Type: application/json
Cache-Control: max-age=3600
Set-Cookie: sessionId=abc123
```

### Important interview point

> Headers carry metadata/control information; the body generally carries the actual request/response data.

# 8. Caching

**Caching means storing a response temporarily so it can be reused instead of making the same expensive request again.**

Example:

```text
First request
Browser → Server
           ↓
        Response
           ↓
         Cache

Second request
Browser → Cache
```

This can improve:

* Performance
* Load time
* Server load
* Network usage

### HTTP caching

Important headers:

```http
Cache-Control
ETag
Last-Modified
Expires
```

Example:

```http
Cache-Control: max-age=3600
```

Means the response can be considered fresh for a specified period.

### ETag

Server sends:

```http
ETag: "abc123"
```

Later browser can ask:

```http
If-None-Match: "abc123"
```

If nothing changed, server can respond:

```text
304 Not Modified
```

and browser can reuse its cached response.

### React angle

You may also encounter application-level caching libraries such as:

* TanStack Query
* SWR
* Apollo Client

These are **application/data caches**, separate from the browser's built-in HTTP caching.

# 9. Cookies

Cookies are small pieces of data associated with a website.

They're commonly used for:

* Sessions
* Authentication
* Preferences
* Tracking

Example:

```http
Set-Cookie: sessionId=abc123; HttpOnly; Secure; SameSite=Lax
```

The browser stores it and may automatically send it with matching requests.

```text
Server
  ↓
Set-Cookie
  ↓
Browser
  ↓
Cookie stored
  ↓
Future request
  ↓
Cookie sent automatically
```

### Important cookie attributes

```text
HttpOnly
→ JavaScript can't directly access it

Secure
→ Sent over HTTPS

SameSite
→ Controls cross-site cookie sending
```

### React interview point

Cookies are different from:

```js
localStorage
sessionStorage
```

Cookies can be automatically included in HTTP requests, while localStorage/sessionStorage are accessed explicitly by JavaScript.

# 10. Same-Origin Policy

**Same-Origin Policy (SOP)** is a browser security mechanism.

It restricts scripts from freely accessing resources/data from a different origin.

An **origin** consists of:

```text
scheme + host + port
```

For example:

```text
https://example.com:443
```

These are different origins:

```text
https://example.com
https://api.example.com
http://example.com
https://example.com:8080
```

because the scheme/host/port differs.

### Why does SOP exist?

Imagine you're logged into:

```text
bank.com
```

Without browser security restrictions, a malicious website could potentially make requests and freely read sensitive data from your bank application.

SOP helps prevent this kind of cross-origin data access.

---

# Same-Origin Policy vs CORS

This is **very commonly asked**.

### Same-Origin Policy

Browser's default security restriction.

```text
app.example.com
       ↓
api.example.com

Different origins
       ↓
Browser restricts certain access
```

### CORS

A mechanism that allows the server to tell the browser:

> "This particular origin is allowed to access my response."

Example:

```http
Access-Control-Allow-Origin: https://app.example.com
```

So:

```text
SOP
 ↓
Restricts cross-origin access

CORS
 ↓
Server can explicitly allow certain cross-origin access
```

# 🔥 Most Important Interview Distinctions

### HTTP vs HTTPS

> HTTP is the communication protocol; HTTPS is HTTP over TLS, providing encrypted and authenticated communication.

### REST vs GraphQL

> REST commonly exposes resource-based endpoints, while GraphQL allows clients to specify the exact data they want through queries.

### 401 vs 403

> **401 = not authenticated**
> **403 = authenticated but not authorized**

### Cookie vs localStorage

> Cookies can automatically be sent with HTTP requests and can be protected using attributes such as HttpOnly and Secure. localStorage is directly accessible to JavaScript.

### SOP vs CORS

> SOP is the browser's same-origin security restriction; CORS is a mechanism that allows servers to explicitly permit certain cross-origin browser requests.

### Headers vs Body

> Headers contain metadata/control information; the body contains the actual request or response payload.
