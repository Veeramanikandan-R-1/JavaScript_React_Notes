# Networking — React Interview Notes

For a **5-year React developer**, focus less on memorizing networking theory and more on understanding **how the browser, React app, API, and server interact**.

---

## 1. HTTP

**HTTP (HyperText Transfer Protocol)** is the protocol used for communication between client and server.

### Request

```http
GET /api/users/10 HTTP/1.1
Host: example.com
Authorization: Bearer token
```

### Response

```http
HTTP/1.1 200 OK
Content-Type: application/json

{
  "id": 10,
  "name": "John"
}
```

### Common HTTP Methods

| Method   | Purpose            | Usually                |
| -------- | ------------------ | ---------------------- |
| `GET`    | Fetch data         | Safe, idempotent       |
| `POST`   | Create/submit data | Not idempotent         |
| `PUT`    | Replace resource   | Idempotent             |
| `PATCH`  | Partially update   | Usually not guaranteed |
| `DELETE` | Delete resource    | Idempotent             |

**Idempotent:** making the same request multiple times has the same intended final effect.

### React example

```js
const response = await fetch("/api/users");
const users = await response.json();
```

---

# 2. HTTPS

**HTTPS = HTTP + TLS encryption**

```text
HTTP
 ↓
TLS encryption
 ↓
HTTPS
```

HTTPS provides:

* 🔒 **Confidentiality** — data is encrypted
* ✅ **Integrity** — data isn't modified in transit
* 🔐 **Authentication** — server identity is verified using certificates

Example:

```text
http://example.com   ❌
https://example.com  ✅
```

### Interview point

HTTPS protects data **while it is traveling between client and server**. It does **not** automatically protect against XSS, bad authorization, insecure APIs, etc.

# 3. REST

**REST (Representational State Transfer)** is an architectural style for building APIs around resources.

Example resource:

```text
/users
/users/10
/products
/products/100
```

### Typical REST API

```http
GET    /users          → Get users
GET    /users/10       → Get user 10
POST   /users          → Create user
PUT    /users/10       → Replace user
PATCH  /users/10       → Update user
DELETE /users/10       → Delete user
```

### React

```js
await fetch("/api/users/10");

await fetch("/api/users", {
  method: "POST",
  headers: {
    "Content-Type": "application/json"
  },
  body: JSON.stringify({
    name: "John"
  })
});
```

### REST characteristics

* Resource-based URLs
* Uses HTTP methods
* Stateless requests
* Usually JSON
* Uses HTTP status codes
* Can be cached

### REST limitation

Suppose UI needs:

```text
User
 ├── name
 ├── email
 └── company
      └── name
```

REST may require multiple endpoints/requests:

```text
GET /users/10
GET /users/10/company
```

This is one problem GraphQL attempts to solve.

---

# 4. GraphQL — Basics

**GraphQL** is an API query language where the client specifies exactly what data it needs.

Instead of:

```http
GET /users/10
```

You might send:

```graphql
query {
  user(id: 10) {
    name
    email
  }
}
```

Response:

```json
{
  "data": {
    "user": {
      "name": "John",
      "email": "john@test.com"
    }
  }
}
```

### Main concepts

**Query** → Read data

```graphql
query {
  users {
    id
    name
  }
}
```

**Mutation** → Modify data

```graphql
mutation {
  createUser(name: "John") {
    id
    name
  }
}
```

**Subscription** → Real-time updates

```graphql
subscription {
  messageAdded {
    id
    text
  }
}
```

### REST vs GraphQL

| REST                             | GraphQL                         |
| -------------------------------- | ------------------------------- |
| Multiple endpoints               | Usually single endpoint         |
| Server determines response shape | Client specifies fields         |
| Can over-fetch/under-fetch       | Helps avoid over/under-fetching |
| HTTP methods have meaning        | Query/Mutation/Subscription     |
| HTTP caching is straightforward  | Caching can be more complex     |

**Interview point:** GraphQL doesn't automatically mean fewer network requests. Poorly designed queries/resolvers can still create performance problems.

# 5. Request Lifecycle

Understand this flow very well:

```text
React Component
      ↓
fetch / Axios
      ↓
Browser
      ↓
DNS Lookup
      ↓
TCP Connection
      ↓
TLS Handshake (HTTPS)
      ↓
HTTP Request
      ↓
Server
      ↓
Authentication / Authorization
      ↓
Business Logic
      ↓
Database / External API
      ↓
HTTP Response
      ↓
Browser
      ↓
React receives data
      ↓
State update
      ↓
Re-render
```

Example:

```js
useEffect(() => {
  fetch("/api/users")
    .then(res => res.json())
    .then(data => setUsers(data));
}, []);
```

### Important distinction

**DNS → TCP → TLS → HTTP**

For HTTPS:

```text
DNS
 ↓
TCP
 ↓
TLS
 ↓
HTTP
```

HTTP itself doesn't perform DNS/TCP/TLS; those are lower layers involved in getting the request delivered.

# 6. HTTP Status Codes

### 2xx — Success

```text
200 OK
201 Created
204 No Content
```

Example:

```http
POST /users
→ 201 Created
```

### 3xx — Redirection / caching-related

```text
301 Moved Permanently
302 Found
304 Not Modified
```

`304` is particularly important for browser caching.

### 4xx — Client-side/request problem

```text
400 Bad Request
401 Unauthorized
403 Forbidden
404 Not Found
409 Conflict
429 Too Many Requests
```

### 5xx — Server problem

```text
500 Internal Server Error
502 Bad Gateway
503 Service Unavailable
504 Gateway Timeout
```

### 401 vs 403 ⭐

```text
401 → Authentication required/failed
403 → Authenticated but not allowed
```

Think:

```text
401 = Who are you?
403 = I know who you are, but you can't do this.
```

# 7. HTTP Headers

Headers contain metadata about requests/responses.

### Common request headers

```http
Authorization: Bearer eyJ...
Content-Type: application/json
Accept: application/json
Cookie: sessionId=abc
Cache-Control: no-cache
```

### Common response headers

```http
Content-Type: application/json
Cache-Control: max-age=3600
Set-Cookie: sessionId=abc
ETag: "abc123"
Access-Control-Allow-Origin: https://myapp.com
```

### `Content-Type` vs `Accept`

```http
Content-Type: application/json
```

Means:

> "The data I am sending is JSON."

```http
Accept: application/json
```

Means:

> "I want JSON in the response."

### Authorization

```js
fetch("/api/profile", {
  headers: {
    Authorization: `Bearer ${token}`
  }
});
```

# 8. Caching

Caching stores previously fetched data so it doesn't need to be downloaded/computed again.

Common layers:

```text
Browser Cache
     ↓
CDN Cache
     ↓
Reverse Proxy
     ↓
Server/Application Cache
     ↓
Database Cache
```

### HTTP caching

Server:

```http
Cache-Control: public, max-age=3600
```

Browser can reuse the response for 1 hour.

### Cache validation

Server:

```http
ETag: "abc123"
```

Later browser:

```http
If-None-Match: "abc123"
```

Server:

```http
304 Not Modified
```

Browser uses its existing cached response.

### React/API caching

Libraries such as **TanStack Query** can cache server state:

```js
const { data } = useQuery({
  queryKey: ["users"],
  queryFn: fetchUsers
});
```

### Important distinction

```text
HTTP Cache
    ≠
React state
    ≠
Server-state cache
```

# 9. Cookies

Cookies are small pieces of data associated with a domain and automatically sent with matching HTTP requests.

Server:

```http
Set-Cookie: sessionId=abc123; HttpOnly; Secure; SameSite=Lax
```

Browser then sends:

```http
Cookie: sessionId=abc123
```

### Important cookie attributes ⭐

#### `HttpOnly`

```http
HttpOnly
```

JavaScript cannot access the cookie through:

```js
document.cookie
```

Useful for reducing token exposure through XSS.

#### `Secure`

```http
Secure
```

Cookie is sent only over HTTPS.

#### `SameSite`

Controls cross-site cookie sending.

```http
SameSite=Strict
SameSite=Lax
SameSite=None; Secure
```

* `Strict` → strongest cross-site restriction
* `Lax` → common default choice
* `None` → allows cross-site usage, requires `Secure`

### React

Usually you **don't manually read an HttpOnly cookie**.

For cross-origin requests where cookies are intentionally needed:

```js
fetch("https://api.example.com/user", {
  credentials: "include"
});
```

Server must also allow credentials through CORS.

### Cookie vs localStorage

| Cookie                           | localStorage                       |
| -------------------------------- | ---------------------------------- |
| Automatically sent with requests | Must manually add                  |
| Supports HttpOnly                | JS accessible                      |
| Supports Secure/SameSite         | No                                 |
| Can be used for session auth     | Often used for client-side storage |
| Subject to CSRF considerations   | XSS can read it                    |

**Interview point:** Don't say "cookies are always safer than localStorage." Security depends on the authentication design and threats being addressed.

# 10. Same-Origin Policy ⭐⭐⭐

**Same-Origin Policy (SOP)** is a browser security mechanism that restricts a web page from freely interacting with resources from a different origin.

An **origin** consists of:

```text
scheme + host + port
```

Example:

```text
https://example.com:443
```

These are different origins:

```text
https://example.com
https://api.example.com     ❌ different host

https://example.com
http://example.com         ❌ different scheme

https://example.com:443
https://example.com:8080   ❌ different port
```

### Same origin

```text
https://example.com/page1
https://example.com/api
```

Same:

```text
scheme = https
host   = example.com
port   = 443
```

# 11. CORS

Although not explicitly in your list, **CORS is directly related to Same-Origin Policy and is very important for interviews.**

Suppose React runs on:

```text
http://localhost:3000
```

API runs on:

```text
http://localhost:8080
```

Different ports → different origins.

Browser may block the frontend from reading the response unless the server allows it.

Server:

```http
Access-Control-Allow-Origin: http://localhost:3000
```

### Preflight

For certain cross-origin requests, browser first sends:

```http
OPTIONS /api/users
```

Server responds with allowed methods/headers.

Then browser sends the actual request.

```text
Browser
  ↓
OPTIONS (preflight)
  ↓
Server
  ↓
Permission granted
  ↓
GET/POST/etc.
```

### Important

**CORS is enforced by browsers.**

It is not an authentication mechanism.
