## 1. Build

**Build = convert source code into something that can be deployed.**

For a React application:

```text
React Source Code
      ↓
npm run build
      ↓
Vite / Webpack
      ↓
Optimized JS + CSS + assets
      ↓
dist/
```

Example:

```bash
npm run build
```

The build process may include:

* Transpiling code
* Bundling
* Minification
* Tree shaking
* Asset optimization

### Interview answer

> "The build step takes the application source code and produces optimized production-ready artifacts."

---

# 2. Test

After building, CI usually runs automated tests.

```text
Code
 ↓
Install dependencies
 ↓
Build
 ↓
Tests
 ↓
Pass / Fail
```

For React, this could include:

* Unit tests
* Component tests
* Integration tests
* End-to-end tests

Example:

```bash
npm test
```

or:

```bash
npm run test
```

### Why?

To catch problems automatically before code reaches production.

> **CI should ideally prevent broken code from being deployed.**

---

# 3. Deploy

**Deploy = make the application available in an environment.**

For a React frontend:

```text
Source
 ↓
Build
 ↓
dist/
 ↓
Upload to hosting/CDN
 ↓
Production
```

For example, the generated static files can be deployed to a static hosting platform or served through a web server/CDN.

Typical environments:

```text
Development
     ↓
Testing / QA
     ↓
Staging
     ↓
Production
```

### Interview answer

> "Deployment takes the validated build artifact and makes it available in the target environment, such as staging or production."

---

# 4. CI/CD

### CI — Continuous Integration

Developers frequently push code/PRs.

The CI system automatically:

```text
Code Push / PR
      ↓
Install dependencies
      ↓
Lint
      ↓
Test
      ↓
Build
      ↓
Pass / Fail
```

The goal is to detect problems early.

---

### CD — Continuous Delivery / Deployment

After validation, the pipeline can deliver/deploy the application.

```text
Git Push
   ↓
CI
   ↓
Lint + Test + Build
   ↓
Deploy
   ↓
Staging / Production
```

**Continuous Delivery** generally means the software is kept in a deployable state, often with a deployment requiring an approval/manual trigger.

**Continuous Deployment** means successful changes can be automatically deployed to production.

# 5. GitHub Actions

**GitHub Actions is a CI/CD automation platform integrated with GitHub.**

You define workflows in YAML files:

```text
.github/
  workflows/
    ci.yml
```

Example simplified workflow:

```yaml
name: CI

on:
  push:
    branches: [main]

jobs:
  build:
    runs-on: ubuntu-latest

    steps:
      - uses: actions/checkout@v4

      - run: npm ci

      - run: npm test

      - run: npm run build
```

Conceptually:

```text
GitHub Push
     ↓
GitHub Actions
     ↓
Install
     ↓
Test
     ↓
Build
     ↓
Deploy
```

### Important terms

**Workflow** → complete automation definition.

**Job** → group of steps executed on a runner.

**Step** → individual action/command.

**Runner** → machine/environment where the job executes.

### Interview answer

> "GitHub Actions allows us to automate CI/CD workflows directly from a GitHub repository, such as running tests, building the React application, and deploying it."

# 6. Jenkins

**Jenkins is a popular automation/CI server.**

It can automate:

* Build
* Test
* Deployment
* Other engineering workflows

Typical flow:

```text
Git Push
   ↓
Jenkins
   ↓
Build
   ↓
Test
   ↓
Deploy
```

### GitHub Actions vs Jenkins

| GitHub Actions              | Jenkins                              |
| --------------------------- | ------------------------------------ |
| Built into GitHub ecosystem | Standalone automation server         |
| Workflow YAML               | Jenkinsfile / pipeline configuration |
| Easy GitHub integration     | Highly customizable                  |
| Managed/self-hosted options | Commonly self-hosted                 |

You don't need to memorize Jenkins configuration for a high-level interview.

### Simple answer

> "Jenkins is a CI/CD automation server. GitHub Actions provides similar automation but is tightly integrated with GitHub."

# 7. Docker — Basics

**Docker packages an application and its dependencies into a container.**

Think:

```text
Application
+
Dependencies
+
Runtime configuration
        ↓
     Docker Image
        ↓
    Container
```

### Why Docker?

Without Docker:

```text
Developer machine
→ Node version X
→ dependencies X
→ environment X

Production
→ Node version Y
→ dependencies Y
→ environment Y
```

Potentially:

> "It works on my machine."

Docker helps make the runtime environment more consistent.

---

## Docker Image

An **image** is a packaged template containing what is needed to run the application.

Example:

```text
Node
+
Application
+
Dependencies
+
Configuration
↓
Docker Image
```

---

## Container

A **container is a running instance of an image**.

```text
Docker Image
     ↓
   Container
```

You can run multiple containers from the same image.

---

## Dockerfile

A `Dockerfile` describes how to build an image.

Simplified React example:

```dockerfile
FROM node:22

WORKDIR /app

COPY package*.json ./
RUN npm ci

COPY . .

RUN npm run build
```

In a production frontend application, you'd commonly use a **multi-stage build** and serve the resulting static files with a lightweight web server.

### Common commands

```bash
docker build -t my-app .
```

Build image.

```bash
docker run my-app
```

Run container.

```bash
docker ps
```

See running containers.

# 🔥 Important Interview Distinctions

### CI vs CD

> **CI:** Automatically validate code through build/tests/etc.
> **CD:** Automatically deliver/deploy validated software.

### Build vs Deploy

> **Build:** Create the production artifact.
> **Deploy:** Put that artifact into an environment where users/services can access it.

### GitHub Actions vs Jenkins

> Both can automate CI/CD. GitHub Actions is tightly integrated with GitHub, while Jenkins is a standalone, highly customizable automation server.

### Docker Image vs Container

> **Image = packaged template.**
> **Container = running instance of that image.**

### Docker vs CI/CD

They're not alternatives.

```text
CI/CD
→ Automation process

Docker
→ Containerization technology
```

Docker can be **one part of a CI/CD pipeline**.
