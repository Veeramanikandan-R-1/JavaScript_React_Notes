# Security — React Interview Notes

For a **6-year React interview**, you mainly need to know **what each attack/protection is, what problem it solves, and how it relates to frontend applications**.

---

## 1. XSS — Cross-Site Scripting

**Problem:** An attacker injects malicious JavaScript into a page.

Example:

```html
<script>
  stealUserData();
</script>
```

If the application renders this as executable HTML, the script can run in the user's browser.

### React

React escapes values rendered through JSX by default:

```jsx
<div>{userInput}</div>
```

So user input is treated as text.

Be careful with:

```jsx
<div dangerouslySetInnerHTML={{ __html: userInput }} />
```

### Prevention

* React's default escaping
* Avoid unnecessary `dangerouslySetInnerHTML`
* Sanitize HTML when HTML rendering is required
* Content Security Policy (CSP)
* Keep dependencies updated

**Remember:**

> **XSS = attacker gets JavaScript to execute in your application.**

---

# 2. CSRF — Cross-Site Request Forgery

**Problem:** An attacker tricks a user's browser into making an unwanted request to a website where the user is already authenticated.

Example:

```text
User logged into bank.com
        ↓
Visits malicious-site.com
        ↓
Malicious site triggers request to bank.com
        ↓
Browser sends authentication cookie
        ↓
Bank may process the request
```

### Prevention

* `SameSite` cookies
* CSRF tokens
* Validate `Origin` / `Referer` where appropriate
* Avoid state-changing operations through GET

**Remember:**

> **CSRF = attacker tricks the browser into making an authenticated request.**

---

# 3. CORS — Cross-Origin Resource Sharing

**CORS is not an attack.**

It is a **browser security mechanism** that controls whether JavaScript from one origin can access resources from another origin.

Example:

```text
Frontend
https://app.example.com

       ↓ API request

Backend
https://api.example.com
```

These are different origins because the hosts differ.

The backend can respond with:

```http
Access-Control-Allow-Origin: https://app.example.com
```

telling the browser that this frontend is allowed to access the response.

### Important interview point

CORS is enforced by the **browser**.

Also:

> CORS is not a replacement for authentication or authorization.

And:

> CORS does not protect your API from non-browser clients such as curl or server-to-server requests.

**Remember:**

> **CORS = browser-controlled rules for cross-origin requests.**

---

# 4. CSP — Content Security Policy

CSP is a security policy that tells the browser **what types/sources of content are allowed to execute or load**.

Example concept:

```http
Content-Security-Policy: script-src 'self'
```

This can tell the browser:

> Only execute scripts from my own origin.

CSP can help reduce the impact of XSS.

### Common directives

```text
script-src
style-src
img-src
connect-src
font-src
```

For example:

```http
Content-Security-Policy: script-src 'self'; img-src 'self' https://cdn.example.com
```

### Important

CSP is a **defense layer**, not a replacement for proper input handling and secure coding.

**Remember:**

> **CSP = browser rules restricting what resources/scripts are allowed to run or load.**

---

# 5. Sanitization

**Sanitization = cleaning/transforming untrusted input before using it in a potentially dangerous context.**

For example, suppose a user enters HTML:

```html
<img src=x onerror="stealData()">
```

If your application needs to render user-provided HTML, you should sanitize it before rendering.

```text
Untrusted HTML
      ↓
Sanitizer
      ↓
Safe HTML
      ↓
Render
```

### Validation vs Sanitization

Simple distinction:

**Validation:**

> "Is this input acceptable?"

**Sanitization:**

> "Remove/transform dangerous parts of this input."

### React

Normally:

```jsx
<div>{userInput}</div>
```

is safer because React escapes the value.

But if you use:

```jsx
dangerouslySetInnerHTML
```

you need to be much more careful about sanitization.

**Remember:**

> **Sanitization = make untrusted data safe for a particular use/context.**

---

# 6. Secure Cookies

Cookies are commonly used for authentication/session management.

Important attributes:

### `HttpOnly`

```text
HttpOnly
```

JavaScript cannot directly read the cookie.

Helps reduce the ability of XSS payloads to steal the cookie value.

---

### `Secure`

```text
Secure
```

Cookie is sent only over HTTPS.

---

### `SameSite`

Controls when cookies are sent in cross-site requests.

Common values:

```text
Strict
Lax
None
```

`SameSite` is particularly important for reducing CSRF risk.

### Example

```http
Set-Cookie: sessionId=abc123; HttpOnly; Secure; SameSite=Lax
```

### Important interview point

`HttpOnly` **doesn't prevent XSS**.

It simply prevents JavaScript from directly reading that cookie.

**Remember:**

> **HttpOnly → protect cookie from JavaScript access**
> **Secure → HTTPS only**
> **SameSite → control cross-site cookie sending**

---

# 7. HTTPS

**HTTPS = HTTP over TLS.**

It encrypts communication between the browser and server.

```text
Browser
   ↕
 HTTPS / TLS
   ↕
Server
```

It provides:

### Confidentiality

Attackers can't easily read data being transmitted.

### Integrity

Helps prevent attackers from modifying data in transit.

### Authentication

TLS certificates help the browser verify that it is communicating with the intended server.

---

### HTTP vs HTTPS

```text
HTTP
Browser ─────────── Server
       readable traffic


HTTPS
Browser ═══════════ Server
          encrypted
```

HTTPS is essential when transmitting:

* Passwords
* Authentication credentials
* Session information
* Personal information
* API data

**Remember:**

> **HTTPS protects data in transit.**

---

# 🔥 Don't Confuse These

This is probably the most useful part for interviews.

| Concept            | Main purpose                                                 |
| ------------------ | ------------------------------------------------------------ |
| **XSS**            | Prevent malicious JavaScript from executing                  |
| **CSRF**           | Prevent unwanted authenticated requests                      |
| **CORS**           | Control browser access to cross-origin responses             |
| **CSP**            | Restrict what scripts/resources the browser can load/execute |
| **Sanitization**   | Clean untrusted input before dangerous use                   |
| **Secure Cookies** | Protect authentication/session cookies                       |
| **HTTPS**          | Encrypt and protect data in transit                          |

### Easy mental model

```text
XSS
→ "Attacker runs my JavaScript"

CSRF
→ "Attacker makes my browser send a request"

CORS
→ "Can this origin access that cross-origin response?"

CSP
→ "Which scripts/resources is the browser allowed to load?"

Sanitization
→ "Can I safely use this untrusted input?"

Secure Cookie
→ "How should authentication cookies be protected?"

HTTPS
→ "Can someone read/modify traffic between browser and server?"
```
