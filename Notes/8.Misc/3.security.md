# Security — React Interview Notes

For a **5-year React developer**, understand the difference between **browser security mechanisms**, **application-level protection**, and **server-side responsibilities**.

> **Important:** Frontend security alone is never enough. Authentication, authorization, validation and sensitive-data protection must ultimately be enforced by the backend.

---

# 1. XSS — Cross-Site Scripting

**XSS = attacker injects malicious JavaScript/content into a page that another user views.**

### Example

Suppose an application renders user input directly:

```jsx
function Comment({ text }) {
  return <div dangerouslySetInnerHTML={{ __html: text }} />;
}
```

Attacker submits:

```html
<img src=x onerror="alert(document.cookie)">
```

If rendered unsafely, the browser may execute the attacker's code.

### Types of XSS

#### Stored XSS

Malicious content is stored on the server/database.

```text
Attacker → malicious comment → Database
                              ↓
                         Other users
```

#### Reflected XSS

Malicious input comes through a request and is immediately reflected in the response.

```text
Attacker → malicious URL → Server → Victim
```

#### DOM-based XSS

Vulnerability occurs primarily through client-side JavaScript manipulating the DOM unsafely.

---

## React and XSS

React escapes values by default:

```jsx
const name = "<script>alert(1)</script>";

return <div>{name}</div>;
```

React renders it as text rather than executing it.

### Dangerous API

```jsx
<div dangerouslySetInnerHTML={{ __html: userContent }} />
```

Avoid this unless HTML is genuinely required.

If required, **sanitize the HTML first**.

### XSS prevention

```text
✓ React's default escaping
✓ Avoid unsafe HTML injection
✓ Sanitize HTML when HTML is required
✓ Validate input server-side
✓ Use CSP
✓ Avoid unsafe DOM APIs
✓ Keep dependencies updated
```

---

# 2. CSRF — Cross-Site Request Forgery

**CSRF = attacker tricks a user's browser into making an unwanted authenticated request to your application.**

Typically relevant when authentication uses **cookies**, because browsers automatically attach cookies to matching requests.

### Attack scenario

User is logged into:

```text
bank.com
```

Attacker creates:

```html
<form action="https://bank.com/transfer" method="POST">
  ...
</form>

<script>
  document.forms[0].submit();
</script>
```

The browser may automatically attach the bank's authentication cookie.

```text
Victim visits attacker.com
        ↓
Attacker triggers request
        ↓
Browser sends bank cookies
        ↓
bank.com receives authenticated request
```

---

## CSRF Prevention

### 1. SameSite cookies

```http
Set-Cookie: session=abc;
SameSite=Lax;
```

Common values:

```text
Strict
Lax
None
```

`SameSite` controls when cookies are sent in cross-site contexts.

---

### 2. CSRF Token

Server generates a random token.

```text
Client → request + CSRF token → Server
```

Server validates the token before performing the state-changing operation.

---

### 3. Check Origin/Referer

Backend can verify that sensitive requests originate from an expected site.

### Important

CSRF is primarily a **server-side request validation problem**.

---

# 3. CORS — Cross-Origin Resource Sharing

**CORS controls whether a browser allows JavaScript from one origin to access resources from another origin.**

Example:

```text
Frontend:
https://app.example.com

API:
https://api.example.com
```

Different origins → browser applies same-origin policy.

Server can explicitly allow the frontend:

```http
Access-Control-Allow-Origin: https://app.example.com
```

### Simple request

```js
fetch("https://api.example.com/users");
```

Browser checks whether the response satisfies CORS rules.

---

## Preflight Request

For certain cross-origin requests, browser sends:

```http
OPTIONS /users
Origin: https://app.example.com
Access-Control-Request-Method: PUT
Access-Control-Request-Headers: Authorization
```

Server responds with permitted values:

```http
Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Methods: GET, POST, PUT
Access-Control-Allow-Headers: Authorization, Content-Type
```

Then browser can send the actual request.

---

## CORS ≠ CSRF

Very common interview question.

| CORS                                     | CSRF                                              |
| ---------------------------------------- | ------------------------------------------------- |
| Controls cross-origin browser access     | Prevents unwanted authenticated actions           |
| Browser security mechanism               | Attack                                            |
| Server sends CORS headers                | Token/SameSite/Origin checks can mitigate         |
| Mainly about reading/accessing responses | Mainly about unauthorized state-changing requests |

**Important:** CORS is **not an authentication mechanism**.

---

# 4. CSP — Content Security Policy

**CSP = browser security policy that restricts where resources/scripts can come from and what content can execute.**

It helps significantly reduce the impact of XSS.

Example:

```http
Content-Security-Policy:
  default-src 'self';
  script-src 'self';
  style-src 'self';
  img-src 'self' https:;
```

Meaning roughly:

```text
Scripts → only same origin
Styles  → only same origin
Images  → same origin + HTTPS sources
```

---

## Useful CSP directives

```text
default-src
script-src
style-src
img-src
font-src
connect-src
frame-src
object-src
base-uri
frame-ancestors
```

### Example

```http
Content-Security-Policy:
  default-src 'self';
  script-src 'self';
  connect-src 'self' https://api.example.com;
  img-src 'self' https:;
  object-src 'none';
```

### Nonce

For applications requiring specific inline scripts:

```http
Content-Security-Policy:
  script-src 'self' 'nonce-abc123'
```

```html
<script nonce="abc123">
  // allowed script
</script>
```

The nonce should be unpredictable and generated appropriately by the server.

### Interview point

> CSP is **defense-in-depth**, not a replacement for proper output encoding/sanitization.

---

# 5. Sanitization

**Sanitization = removing or neutralizing dangerous content from untrusted input before using it in a sensitive context.**

Example malicious HTML:

```html
<img src=x onerror="alert('XSS')">
```

A sanitizer can remove unsafe attributes/elements.

### React example

If HTML must be rendered:

```jsx
<div
  dangerouslySetInnerHTML={{
    __html: sanitizedHtml
  }}
/>
```

Conceptually:

```text
User HTML
    ↓
Sanitizer
    ↓
Safe HTML
    ↓
dangerouslySetInnerHTML
```

### Important distinction

**Validation vs sanitization**

```text
Validation
→ Is this input acceptable?

Sanitization
→ Remove/neutralize dangerous parts.
```

Example:

```text
Email → validate format
HTML  → sanitize allowed HTML
```

### Best practice

Don't blindly sanitize everything.

Instead:

1. Understand the output context.
2. Prefer React's automatic escaping.
3. Sanitize only when HTML/content actually needs to be interpreted.
4. Use a well-maintained, context-aware sanitizer.

# 6. Secure Cookies

Cookies are commonly used for sessions/authentication.

### Important cookie attributes

```http
Set-Cookie:
  sessionId=abc123;
  Secure;
  HttpOnly;
  SameSite=Lax;
  Path=/
```

### `HttpOnly`

```text
JavaScript ❌ cannot access cookie
Browser     ✅ can send cookie with requests
```

Helps reduce the ability of injected JavaScript to steal the cookie.

```js
document.cookie
```

won't expose an `HttpOnly` cookie.

---

### `Secure`

Cookie is sent only over HTTPS connections.

```http
Secure
```

---

### `SameSite`

Controls cross-site cookie sending behavior.

```text
Strict → strongest cross-site restriction
Lax    → common/default-friendly option
None   → cross-site usage; requires Secure
```

---

### `Path`

Restricts which URL paths receive the cookie.

```http
Path=/
```

---

### `Domain`

Controls which host/domain can receive the cookie.

Avoid unnecessarily broad domain scope.

---

## Secure Cookie Example

```http
Set-Cookie:
  sessionId=abc123;
  HttpOnly;
  Secure;
  SameSite=Lax;
  Path=/;
```

### Where should authentication token be stored?

There isn't a universal answer.

A common secure architecture is:

```text
Browser
   ↓
HttpOnly + Secure + SameSite cookie
   ↓
Session / authentication
```

Advantages:

* JavaScript cannot directly read an HttpOnly cookie
* Browser automatically manages it

But cookie-based authentication requires careful **CSRF protection**.

### localStorage warning

```js
localStorage.setItem("token", token);
```

JavaScript can read this token, so if your application has an XSS vulnerability, malicious JavaScript may steal it.

# 7. HTTPS

**HTTPS = HTTP over TLS.**

It provides:

```text
Confidentiality
+
Integrity
+
Server authentication
```

### HTTP

```text
Client ────────> Server
       readable traffic
```

### HTTPS

```text
Client
   ↓
Encrypted TLS connection
   ↓
Server
```

Attackers on the network should not be able to simply read or modify the protected traffic.

---

## TLS provides

### 1. Encryption

Protects data from being read in transit.

### 2. Integrity

Helps detect tampering.

### 3. Authentication

Certificates help the client verify the server's identity.

---

## HTTPS + Secure Cookies

`Secure` cookies should be transmitted only over HTTPS.

```http
Set-Cookie: session=abc; Secure; HttpOnly
```

# 🔥 Common Interview Questions

### 1. Is React protected against XSS?

**Partially by default.**

React escapes values rendered through normal JSX:

```jsx
<div>{userInput}</div>
```

But unsafe APIs such as:

```jsx
dangerouslySetInnerHTML
```

can introduce XSS if untrusted content isn't handled safely.

---

### 2. Can HttpOnly completely prevent XSS?

**No.**

It prevents JavaScript from directly reading the cookie, but injected JavaScript can potentially still perform actions as the user through the application.

Therefore:

```text
HttpOnly ≠ XSS prevention
```

It's one layer of defense.

---

### 3. CORS vs Same-Origin Policy?

**Same-Origin Policy (SOP)** is the browser's fundamental restriction on cross-origin interactions.

**CORS** is a mechanism that allows servers to selectively relax certain browser restrictions for cross-origin resource access.

---

### 4. Does CORS protect the backend API?

**No.**

CORS primarily controls **browser behavior**.

A malicious client such as:

```text
Postman
curl
custom backend
```

doesn't have the browser's CORS enforcement.

Therefore authentication and authorization must still be enforced by the server.

---

### 5. XSS vs CSRF?

```text
XSS
→ Attacker executes code in your application's origin.

CSRF
→ Attacker tricks the browser into making an authenticated request.
```

---

### 6. How do you protect a React application?

A strong senior-level answer:

```text
✓ HTTPS everywhere
✓ Secure + HttpOnly + SameSite cookies where appropriate
✓ CSRF protection for cookie-authenticated state changes
✓ React's default escaping
✓ Avoid unsafe HTML injection
✓ Sanitize required HTML
✓ Strong CSP
✓ Proper CORS configuration
✓ Server-side input validation
✓ Server-side authorization
✓ Secure dependency management
✓ Don't expose secrets in frontend code
✓ Don't store sensitive secrets in localStorage
```

---

# ⭐ Senior-Level Mental Model

Think in **layers**, not one magic security solution:

```text
HTTPS
  ↓
Protect data in transit

Secure Cookies
  ↓
Protect authentication credentials

SameSite / CSRF Token
  ↓
Protect cookie-authenticated requests

React Escaping + Sanitization
  ↓
Reduce XSS risk

CSP
  ↓
Limit what injected scripts can execute/load

CORS
  ↓
Control browser cross-origin resource access

Backend Auth + Authorization
  ↓
Final security boundary
```

### Most important interview statement

> **Never trust the frontend.** React can improve client-side security, but authorization, validation, authentication and sensitive business rules must always be enforced on the backend.
